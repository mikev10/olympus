CONTEXT YOU NEED

The runtime runs an AI agent that changes a repository, then judges the change
by running checks (test suites, pinned commands) over a tree the runtime builds,
in a container mounted read-only with no network. Until this change, those
checks ran over whatever `node_modules` the base snapshot held, so a change
needing a new dependency could not pass. Now, before the base is judged and
before each task's checks, the runtime installs the tree's lockfile
(`package-lock.json` or `pnpm-lock.yaml`) in a separate container whose network
reaches only the registries a policy file grants, with lifecycle scripts
disabled and every package required to carry an integrity hash, and copies the
result into the read-only tree the checks run over, replacing every
`node_modules` the tree held. The evidence record carries the lockfile's diff
against the base and a digest of the installed tree.

It must hold against a capable, motivated party trying to make a change pass
its checks without the change being good: by getting code it wrote to run, or
to be loaded as a dependency or a test runner, in a place the runtime trusts;
by getting the install to reach the network beyond what policy grants; or by
getting checks to run over dependencies other than an install of the lockfile
that the runtime verified. Assume no deceptive intent — only that the easiest
path gets taken.

That party controls every file in the working tree it hands back, the lockfile,
`package.json` files, `.npmrc`, `.pnpmfile.cjs`, and anything under
`node_modules` included, and controls which of them exist. It does not control
the policy file, the installer declarations in code, the images they are pinned
to, or the components the runtime is wired with — the Vault, the sandbox
provider, and the drivers are runtime-selected and trusted, even where a
function takes one as an argument — and it does not control code running inside
the runtime's own process. The registries policy grants are trusted to serve
what they serve; the lockfile's hashes are what binds what is installed.

The invariants at stake:

- No agent writes to the Vault, the runtime's evidence store, at any level, in
  any repository, in any role.
- An agent may not be judged by an artifact it can write: what judges a change
  (its tests, the runner that executes them, the record of what ran) must be
  out of the changing agent's reach.
- Default deny: a capability not granted in policy is unavailable. Network
  access for an install exists only for registries the policy lists.
- Fail closed: a missing check, an unsupported stack, an unreadable lockfile,
  or an install that did not complete is a refusal, never a silent degrade or a
  warning that lets the run continue.
- Every capability claim maps to an executable assertion that fails when the
  capability is deleted.

The mechanisms that matter most:

- The install plan (`planInstall`) and the per-installer lockfile readers that
  decide what is installed, what is refused, and which packages count as
  verifiable by hash.
- `installInto`: which files enter the install's container, how the install is
  keyed and reused within a run, and how the result replaces the dependency
  trees in the tree the checks mount.
- Where the install is wired: admission, the base run, and `verify`, and what
  each does when the install is refused, fails, or cannot be provisioned.
- The conformance assertions and the stand-in installer the tests use.
