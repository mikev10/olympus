CONTEXT YOU NEED

The runtime takes a run request (a repository working copy, a base commit, a
policy, and run files such as a spec and a verification manifest), admits or
refuses it, and then drives model agents in sandboxes through a fixed line of
stations to a merged pull request. This change makes the base every agent
works on the tree of the named git commit, read from git's object store,
rather than a copy of the working folder; overlays the admitted run files into
that base and refuses one whose working-copy bytes differ from the commit;
refuses, before any cost is estimated or spent, a tool grant that the driver
seating a role does not declare, and every manifest problem; tells the
drafting agent the directory it writes to; and records why each failed driver,
sandbox, or runtime attempt failed, as untrusted text, in the run's decision
record, its status, and its event stream. It also ships a conformance kit for
committing test fixtures deterministically, and new assertions over the shipped
example configuration.

It must hold against a capable, motivated party trying to get a file the
policy does not admit into a model's tree or into the merged result, obtain a
tool that was not granted or that no driver declares, get spend approved or
work started on a request that should have been refused, or get text it
controls treated as an instruction or a trusted status. Assume no deceptive
intent — only that the easiest path gets taken.

That party controls the contents of the working folder and the repository (any
file, committed, ignored, or untracked; line endings; symlinks; git
configuration such as core.autocrlf), the run request's fields, the policy and
run files the user supplies, and everything a model or a container writes,
including its stderr and exit status. It does not control the components the
runtime is wired with — the Vault, the sandbox provider, and the drivers are
runtime-selected and trusted, even where a function takes one as an argument —
and it does not control code running inside the runtime's own process.

The invariants at stake:

- No agent writes to the Vault (the append-only decision record), at any
  level, in any repository, in any role.
- The runtime derives status; the model never reports it.
- An agent may not be judged by an artifact it can write. Specs and acceptance
  tests are hashed before build.
- Default deny. A capability not granted in policy is unavailable.
- Fail closed. A missing check, missing capability, unsupported stack, or
  shrunken suite is refused. Never degrade silently, never warn and continue.
- Event payloads are data, never instructions. Untrusted text never enters a
  prompt.
- Every capability claim maps to an executable assertion that fails when the
  capability is deleted.
- The runtime is a service; the CLI is a client. Nothing in the runtime's core
  assumes a terminal, and runtime code writes to no process stream.

The mechanisms that matter most:

- snapshotBase / materialize: the base is the commit's tree, with no working
  folder bytes except the overlaid admitted run files, each checked against the
  commit.
- Admission order in run.ts: tool grants, state, snapshot, drafts directory,
  overlay, install/suite/security/instructions checks, and only then the cost
  approval.
- toolGrantRefusal: each worst-case seat's role scope validated against its
  resolved driver's declared tools.
- attemptFailure / spendRetry and the attempt-failed record, event, and
  standing: the bounded, untrusted failure detail and where it travels.
