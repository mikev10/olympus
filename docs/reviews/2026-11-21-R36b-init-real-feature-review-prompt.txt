CONTEXT YOU NEED

The runtime carries a change from a one-line intent to a merged pull request through a fixed line of stations: models draft a spec and acceptance tests, a person approves them, they are hashed and locked, a model builds the change in a sandbox, and the runtime verifies, scans, reviews, and opens the pull request. This unit adds `factory-host init` (packages/api/src/init.ts), which detects a repository's stack and writes the setup a first run needs: a policy, role prompts, rubrics, and the host's environment file in a config directory outside the repository, and a verification manifest and a task graph under the repository's `.factory/`. The host and the CLI read that environment file with `--env-file`. The host refuses to start where a container user is required and missing, or where its port cannot be bound. A real run on a real application produced four fixes:
- the test drafter's role names every field of a check;
- a security scan's copy of the tree leaves out dependency directories (packages/api/src/scan.ts);
- the line that tells the test drafter where to write names the test directory at the tree's root (packages/api/src/drafting.ts);
- the token budgets of the seats that read the repository are raised, with the dollar budgets unchanged (setup/policy.yaml, examples/policy.yaml).

It must hold against a capable, motivated party trying to get a change merged that the line's checks should have stopped, or to run a model with more access than the policy grants. Assume no deceptive intent — only that the easiest path gets taken.

That party controls the contents of the repository the line works on (every file and directory name in it, including what a model wrote during an earlier station), what a model returns or writes during a run, and the intent text. It does not control the components the runtime is wired with — the Vault, the sandbox provider, the security scanners' images, and the model drivers are runtime-selected and trusted, even where a function takes one as an argument. It does not control the operator who runs `init` and starts the host, or the config directory outside the repository that `init` writes, or code running inside the runtime's own process.

The invariants at stake:

- No agent writes to the Vault, the runtime's append-only record of a run, at any level, in any repository, in any role.
- The runtime derives a task's status; a model never reports it.
- An agent may not be judged by an artifact it can write. Specs and acceptance tests are hashed and locked before the build, and the policy, roles, and rubrics a run is judged by sit outside any tree a model can write.
- Default deny: a capability not granted in policy is unavailable.
- Fail closed: a missing check, missing capability, unsupported stack, or shrunken test suite is a refusal. Never degrade silently, never warn and continue.
- The runtime is a service and the CLI is a client: nothing in the core assumes a terminal, and the CLI takes no runtime package as a dependency.
- Every capability claim maps to an executable assertion that fails when the capability is deleted.

The mechanisms that matter most:

- What `init` writes, where, and its refusal to overwrite any existing file or to write a manifest for an unsupported or ambiguous stack (packages/api/src/init.ts).
- The security scan's copy of the tree, which now leaves out directories named as dependency trees (`node_modules`, `.venv`, `site-packages`, `__pycache__`, matched case-insensitively), and the scanner run over that copy (packages/api/src/scan.ts).
- The host's start-up checks: reading `--env-file`, the container user required on Windows, a port it cannot bind (packages/api/src/host/config.ts, host/main.ts), and the CLI's own `--env-file` (packages/cli/src/cli.ts).
- The conformance entries that assert these and fail when the check is deleted (packages/conformance/src/registry/init.ts and the changed entries).
