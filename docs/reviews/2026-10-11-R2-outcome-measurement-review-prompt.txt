CONTEXT YOU NEED

The project runs AI coding agents through a fixed line of stations (build,
verify, review, integrate, and others) and records what happened in a
write-once store called the Vault: an admission record per run, versioned run
state, one evidence bundle per verified attempt, one usage (cost) record per
model call, one enforcement decision per refusal, approval, or park, and an
integration record when the change is pushed and merged on GitHub. This change
adds `outcomes()`, which reads every run the Vault lists and derives rates —
a caught false-done rate (attempts the agent ended that the runtime did not
pass, or whose claim contradicted the evidence), autonomy ratio, first-pass
yield, approval wait, cycle time, cost per merged change — each with its
sample size and a one-sided 95% Clopper–Pearson bound. It also adds two
fields to the store's contract (a merge time taken from GitHub, and a way to
list every run), a likely-cost estimate shown beside a run's worst-case cost,
an HTTP route and CLI command that serve the rates, and a field on the per-run
report saying whether its standing was read from records or from a live check
of the working copy. The range also contains one earlier commit that adds
conformance fixtures for a repository-readiness scanner; review it with the
same rigor.

It must hold against a capable, motivated party trying to make the line look
safer, more autonomous, faster, or cheaper than its records show — or to make a
rate appear where there is no data behind it. Assume no deceptive intent —
only that the easiest path gets taken.

That party controls what the model returns (its claims, its narrative, the
files it writes in its workspace), the files in the target repository, when
the process stops and is resumed (so records may be written twice, or a write
may be lost mid-call), and the query parameters an authenticated caller sends
to the HTTP route. It does not control the components the runtime is wired
with — the Vault, the sandbox provider, the drivers, and the GitHub integrator
are runtime-selected and trusted, even where a function takes one as an
argument — and it does not control code running inside the runtime's own
process.

The invariants at stake:

- The runtime derives status; the model never reports it. An agent's account
  is a claim, stored apart from evidence, and every published figure must come
  from records the runtime wrote, never from anything a model returned.
- Fail closed. A missing input, an empty sample, an unknown cost, or an
  unsupported case is reported as such — never as a zero, a pass, or a
  silently narrower figure.
- Every capability claim maps to an executable assertion that fails when the
  capability is deleted.
- Any rate the system shows can be recomputed from the stored records alone;
  nothing in a published figure depends on what a workspace holds at read time.

The mechanisms that matter most:

- Attempt outcome: each evidence bundle is one attempt; it counts as passed
  only if it is the last bundle for its task and the task's recorded status is
  passed; a passed attempt whose claim differed from the evidence is still a
  caught false-done.
- Population: the Vault, not the caller, names the runs; each run's ending
  (refused, merged, passed, cancelled, halted, parked, unfinished) is read from
  records alone, and unfinished runs are counted but kept out of run-level
  rates.
- Bounds and absence: Clopper–Pearson bounds on the side that matters,
  `no-sample` for an empty sample, cost marked a lower bound when any call's
  cost is unknown, and a cost estimate that declines below five past tasks per
  station and model.
- The merge time: taken from GitHub's pull request on the merge and on a
  resume that finds it already merged, never from the runtime's clock.
