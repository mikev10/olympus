CONTEXT YOU NEED

The runtime carries a change through fixed stations. At `test-design` it locks the acceptance tests and a verification manifest (a list of checks, each a pinned argument vector); at `verify` it runs those checks over the base plus the change, and a task passes only if its required checks pass. A check that already passes on the unchanged base would pass whatever the change did, so this unit makes each acceptance check, and optionally each behavioral check, declare whether it 'fails' or 'passes' on the base, refuses at admission a manifest with no required check declared 'fails', runs every declared check over a fresh read-only copy of the base at the `test-design` exit before any model is invoked, records the results once in a runtime-only store (the Vault), and refuses the exit when a check does not do what it declared. The evidence written at `verify` points to that record.

It must hold against a capable, motivated party trying to get a change accepted by a gate that never required the change: a manifest whose 'fails' check does not actually fail on the base, a reproduction that 'fails' only because it never ran, or a run that crosses `test-design` without its base being judged. Assume no deceptive intent — only that the easiest path gets taken.

That party controls the verification manifest and the acceptance test files submitted with a run (their content, kinds, declarations, and commands), the repository contents that make up the base, what the model writes during `build`, and when the runtime process stops (a run may be resumed from any committed state). It does not control the components the runtime is wired with — the Vault, the sandbox provider, the workspace store, and the drivers are runtime-selected and trusted, even where a function takes one as an argument — and it does not control code running inside the runtime's own process.

The invariants at stake:

- The runtime derives status; the model never reports it. Results are collected by the runtime from processes it ran; nothing a model returned decides an outcome.
- An agent may not be judged by an artifact it can write. Specs and acceptance tests are hashed before build and re-verified at every station transition.
- Fail closed. A missing check, a check that did not start, an unsupported stack, or a test suite that enumerates below what was expected is a refusal — never a silent degrade or a warning that lets the run continue.
- Default deny. A check sandbox has no network unless policy grants it.
- No agent writes to the Vault.

The mechanisms that matter most:

- `parseManifest` in packages/api/src/validate.ts: which declarations are required, allowed, and refused, and what counts as the reproduction
- `runOnBase` and the `test-design` case of `work` in packages/api/src/line.ts: what the checks run over, in what sandbox, what is recorded, and how a resume and a refusal behave
- `baseMismatches` / `baseRefusal` in packages/api/src/base.ts: how a record becomes a refusal, including the suite-count rule
- `recordBaseRun` / `readBaseRun` in the two Vault implementations: write-once, shape checks, and reading by reference
