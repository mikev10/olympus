CONTEXT YOU NEED

The project runs AI agents that change code in a target repository at one of
four autonomy levels, L0 (manual) to L3 (autonomous), where a policy engine
decides the highest level a run may have. The new package
`packages/readiness` scans one target repository at one commit — copying the
commit's tree out of git, then running probes over that copy, most of them as
commands in fresh Docker sandboxes — and derives a ceiling of L0, L1, or L2
with the probe that holds it there. `resolveWithReadiness` applies that
ceiling as a fourth term beside the policy's global cap, station cap, and role
ceiling: it may only lower the level a run gets, and a refusal must name every
term that bound it. The conformance assertions in
`packages/conformance/src/registry/readiness.ts` and the two fixtures under
`packages/conformance/fixtures/types/` are the executable statement of those
properties.

It must hold against a capable, motivated party trying to obtain a higher
autonomy ceiling than the repository actually supports, or to make applying a
readiness result grant a run more than the policy alone would. Assume no
deceptive intent — only that the easiest path gets taken.

That party controls the content of the target repository at the scanned
commit: every tracked file, including `package.json` and its scripts, the
lockfile, test files and test configuration, file names, file modes, symlinks,
and submodule entries, and therefore whatever code runs when the scan installs,
builds, or tests that tree inside a sandbox. It does not control the
components the scan is wired with: the sandbox provider, the policy engine, the
images named in the scan options, the branch-protection checker, the `git`
binary on the host, and the scan options themselves are supplied by the
runtime and trusted, even where a function takes one as an argument. It does
not control code running inside the runtime's own process.

The invariants at stake:

- The runtime derives status; the model never reports it. A probe's outcome is
  computed by the runtime from what it observed, never supplied by a model or a
  driver.
- Default deny. A capability not granted in policy is unavailable; a readiness
  result may lower an autonomy level or leave it alone, and may never raise
  one or grant what policy withheld. A repository with no scan keeps exactly
  what policy gives it, and that absence must be an explicit state, never an
  undefined value that reads as clearance.
- Fail closed. A probe that could not execute (timeout, provisioning failure,
  missing tool, missing adapter) derives exactly as a probe that failed, never
  higher; an unsupported stack is refused rather than reported as an empty but
  clean suite.
- Every capability claim maps to an executable assertion that fails when the
  capability is deleted. Every probe declared ceiling-bearing must have such an
  assertion.
- No agent writes to the project's own record store, and a scan never writes to
  the target repository: the repository must be byte-identical after a scan.

The mechanisms that matter most:

- `deriveCeiling` and the probe tiers in `probes.ts`: which outcomes reach L1 and L2.
- `resolveWithReadiness`: the engine's verdict plus the readiness term, and attribution of each bounding cap.
- `materialize` in `tree.ts`: copying the commit's tree out of git onto the host without writing to the repository or outside the copy.
- `scan` in `scan.ts`: which probe is executed, static, or answered by the checker, how each outcome is judged from an exit code or a read, and the order in which probes see the copied tree.
