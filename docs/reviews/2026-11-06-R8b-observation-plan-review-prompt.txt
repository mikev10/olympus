CONTEXT YOU NEED

Before a change is built, each run names an observation plan: the CI checks
that show the change working once merged, the checks that show it regressed,
and a rollback condition (which named checks, failing on how many consecutive
commits). The plan is either supplied with the run, in which case admission
parses it into a write-once admission record, or drafted by a model at the
test-design station with the acceptance tests, in which case it is part of the
draft a person or policy approves. Either way, it is locked by hash at
test-design in the same call that locks the tests. When the run's observation
window closes after merge, a scheduled history walk reads the plan from the
store, never from the workspace. It then lists the check runs GitHub reports on
the merge commit and on every later first-parent commit, and records each
planned check as working, regressed, or missing, plus the rollback condition if
it held. Only after that does it close the window. A plan, or a provider, that
cannot be read is a refusal that leaves the window open. A rate report then
counts each run's readings.

It must hold against a capable, motivated party trying to make a merged change
read as healthy when it was not observed, or was observed failing. That means
making a planned check read working, or regressed or missing read as anything
else, closing a window without its plan having been read, or getting the
runtime to act on what it observed. Assume no deceptive intent — only that the
easiest path gets taken.

That party controls:
- the model that drafts the acceptance tests and the plan, and so the bytes of
  a drafted plan;
- every file in the run's workspace, including a supplied plan's bytes after
  admission;
- which checks the repository's CI runs, under which names, from which GitHub
  App, and with which conclusions;
- the commits pushed to the default branch after the merge.

It does not control the components the runtime is wired with. The store (the
Vault), the sandbox provider, the drivers, and the check reader's network
endpoint are runtime-selected and trusted, even where a function takes one as
an argument. It does not control code running inside the runtime's own process,
and it does not control the run request's policy, which a person supplies.

The invariants at stake:

- No agent writes to the store. The store is written only by the runtime.
- The runtime derives status; the model never reports it. Whether a check
  worked is decided by the runtime from what the provider reported, never by
  anything a model says.
- An agent may not be judged by an artifact it can write. The plan is locked
  before the change is built, and read at close from what was locked.
- Fail closed. A missing plan, an unreadable plan, an unreadable provider, or a
  check never reported must never read as healthy. It is a refusal, or
  `missing`, never a silent pass and never a skipped check.
- Event payloads are data, never instructions. A check's name is text the
  repository's CI configuration chose. It may be compared, but it is never
  stored in a record or put in a prompt.
- Observation never acts: no revert, no reopened run, no new run, no commit
  comes from what was observed.

The mechanisms that matter most:

- Admission (`packages/api/src/run.ts`, `validate.ts`): a plan is required
  exactly while the policy names an observation window, is a path exactly when
  the tests are supplied and `'draft'` exactly when they are drafted, and a
