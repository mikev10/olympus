CONTEXT YOU NEED

The project runs code an AI agent wrote inside a Docker container (the
"sandbox") and then decides, in its own host process, whether that code meets
acceptance criteria. For an HTTP product, a scenario names a command that
starts the product's server (run detached inside the sandbox), a port, and a
list of requests with the responses expected. The sandbox provider sends the
requests from a separate, short-lived "probe" container that joins the
sandbox's network namespace (`docker run --network container:<sandbox>`) but
not its filesystem or process tree; the probe reports raw status, headers, and
bodies as JSON, and the comparison against the expected responses runs on the
host. Stack detection offers this HTTP check only for a provider that has a
probe.

It must hold against a capable, motivated party trying to make an HTTP
behavioral check pass when the product does not actually answer as expected —
or trying to use the check to reach something the sandbox could not reach
itself. Assume no deceptive intent — only that the easiest path gets taken.

That party controls everything that runs inside the sandbox container: the
product's source and binaries, any process it starts, every file the container
can write, and every byte the product sends over the network, including on the
loopback interface the probe shares. It does not control the scenario (its
expected responses come from locked acceptance criteria), and it does not
control the components the runtime is wired with — the sandbox provider, the
Docker daemon, the probe's pinned image and source, and the adapter are
runtime-selected and trusted, even where a function takes one as an argument —
and it does not control code running inside the runtime's own process.

The invariants at stake:

- The runtime derives status; the model never reports it. A verdict is the
  runtime's own comparison of evidence the runtime collected, never a report
  produced by the code being judged. For an HTTP check, what the client
  observed must be observed by a client the product cannot replace or tamper
  with, and the comparison must run where the product cannot reach.
- Fail closed. A missing control, an unsupported provider, a malformed
  scenario, a server that never listens, or an error must be a refusal or a
  failed check — never a silent pass, a skip, or a degraded check that still
  reports success.
- Default deny. A capability not granted is not available. The probe must not
  give the sandbox any network reach it did not already have: a sandbox with
  networking disabled stays with networking disabled, and the probe connects
  to the sandbox's own loopback and nowhere else.
- Every capability claim maps to an executable assertion that fails when the
  capability is deleted. The conformance entries added here must fail if the
  property they name stops holding.

The mechanisms that matter most:

- The probe's isolation: `probeRunArgs` and `LocalDockerProvider.probe` —
  namespace join, read-only root, dropped capabilities, no mounts, removal on
  sandbox teardown, and the wall-clock budget.
- The probe source (`PROBE_SOURCE`) and `readProbeOutput`: what it can be made
  to report, and how the host parses it.
- `readHttpScenario` and `compareHttp`: whether any response that does not
  match the expectation can be judged as holding, and whether any malformed
  scenario is accepted.
- Stack detection and the one-scenario-per-sandbox rule in
  `HttpBehavioralAdapter`, and the three conformance entries in
  `packages/conformance/src/registry/http.ts`.
