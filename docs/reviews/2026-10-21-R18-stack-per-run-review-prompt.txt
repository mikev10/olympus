CONTEXT YOU NEED

The runtime carries an AI agent's work on a repository through a fixed line of
gated stations. When a run is admitted, the runtime inspects the base
repository with an "adapter set" that detects its test framework and major
version (for example `vitest@4`), or `unsupported` where it detects none, and
writes a write-once admission record to a store the agent cannot write (the
Vault). This change adds that detected stack to the admission record, makes the
store refuse an admission record that names no stack, and has the outcome
measurement (false-done rate, autonomy ratio, first-pass yield, each with a
sample size and a confidence bound) keep those rates per stack. A run whose
record names no stack — one admitted before this change, or one refused at
admission — is reported under the key `unrecorded`. These per-stack rates are
meant, later, to decide whether a given stack may run with less human
oversight, so a rate filed under the wrong stack, or a run silently dropped from
or added to a stack's sample, would grant oversight relief on evidence that does
not support it.

The commit range also contains two earlier changes that have not been reviewed:
an amendment that makes a parked task record the cause of its park in run state,
and a README update. Review them as part of the bundle. The range also carries a
test-only change to a sandbox test that now checks its own sandbox's proxy names
rather than every such object on the Docker host.

It must hold against a capable, motivated party trying to make a stack's
recorded rates look better than the runs on that stack were, or to have a run
counted under a stack other than the one the runtime detected. Assume no
deceptive intent — only that the easiest path gets taken.

That party controls the contents of the repository the run targets (including
its package.json and any config files), what the agent returns from each task,
and when the process stops, including between any two writes. It does not
control the components the runtime is wired with — the Vault, the sandbox
provider, the drivers, and the scanners are runtime-selected and trusted, even
where a function takes one as an argument — and it does not control code running
inside the runtime's own process.

The invariants at stake:

- The runtime derives status; the model never reports it. An agent's account of
  its work is a claim, stored apart from the evidence; every rate is derived
  from runtime records, never from what a model said.
- Fail closed. A missing required check, an absent capability, an unsupported
  stack, or a missing record is a refusal or an explicit "not established",
  never a silent degrade, a guessed value, or a warning that lets the run
  continue.
- No agent writes to the Vault. Every Vault mutator is a named operation the
  runtime calls; nothing inside a task's workspace can reach one.
- Every capability claim maps to an executable assertion that fails when the
  capability is deleted.
