# Triage of the TOOLING reviews, 2026-09-21

The external-review runner and the four skill files that operate it, reviewed by
both families on the automation's first real run — it reviewed its own code. The
reviews are `2026-09-21-TOOLING-review-automation-review-codex.md` and
`-review-gemini.md`, each headed with the provenance derived from its manifest.

**No finding was rejected outright, and six held only in part.** In every one of
those six the described mechanism was real and the consequence was overstated —
usually by assuming an actor with access the design does not grant them. That
distinction is the whole of this triage: fixing all ten as written would have
made changes with no defect behind them, and dismissing the six would have left
four real defects in place.

Verification was done by subagents with fresh context, each given one finding as
quoted untrusted material and the file it cites, and not told who wrote the code.
Three findings were settled by execution rather than by reading, and those three
are marked below.

### codex-1 — forged vendor telemetry reaches `counted` — holds

**Checked:** traced both paths from a hypothetical response to `outcomeOf`.

**Found:** the mechanism is exactly as described. A Gemini response carrying
`finishReason: STOP`, the four markers in its text, and an inflated
`promptTokenCount` yields complete ingestion, a verified echo, and `counted`. The
Codex path is the same with an inflated `input_tokens` and `approval_policy:
"never"` in the rollout log. The code cannot distinguish a genuine response from
a same-shaped forgery beyond TLS to a pinned endpoint.

**But the consequence turns on who produces those fields, and the prompt's
framing was wrong about that.** `usageMetadata.promptTokenCount` is generated by
Google's API service, not by the model whose text is under review; the rollout
log is written by the locally installed Codex CLI process, not by OpenAI's
servers. The reviewing model cannot set either. The prompt told the reviewer that
the adversary controls "the content of the vendor's session log and API
response", which hands it the telemetry as well as the text. Under that boundary
the reviewer's conclusion follows, and it is the prompt that was too generous —
this is item 7 of the prompt working exactly as intended.

**Outcome — fix (documentation) and a recorded limit.** The trust boundary is
restated wherever it appears: the reviewing **model** is untrusted; the vendor's
API service and the locally installed CLI are trusted. Claims that the token
count "cannot be faked" are corrected to say precisely who cannot fake it, and
that a token total is a lower-bound heuristic, not proof that every byte arrived.
Against an adversarial vendor no check in this design holds, and that is recorded
rather than defended. No check is weakened; the claims about them are corrected.

### codex-2 — an encoded credential evades the leak scan — holds in part

**Checked:** `findLeakedSecrets` and its matcher, how the Gemini session record
is built, and where the API key is read and sent.

**Holds:** the matcher is a contiguous-substring test, so a credential split
across a character array defeats it; and the whole `usageMetadata` object is
written verbatim into the committed session file, so an unexpected property on it
would be retained.

**Does not hold:** the scenario needs the party producing the reply to know the
key. It cannot. The Gemini key is read from the environment and sent only in the
`x-goog-api-key` header; it never enters the request body, the prompt, or the
model's context. The reviewing model has no access to the value it would have to
encode.

**Outcome — fix, narrowly, and a recorded limit.** The session record stores a
validated set of `usageMetadata` fields rather than an arbitrary object: storing
whatever a vendor returns, verbatim, in a committed file is worth removing on its
own merits. The limit is recorded plainly: no substring scanner defeats a
credential-aware adversary that can emit arbitrary text, so the scan is an
accidental-plaintext-leak detector and is described as one.

### codex-3 and gemini-4 — bundle text reaches the model as instructions — holds

**Raised independently by both families.** Agreement raised its priority; it did
not substitute for checking it.

**Checked:** `composePayload`, the Gemini request body, and the Codex stdin path.

**Found:** confirmed in full. The bundle is inserted verbatim with no escaping.
The Gemini request places instructions and bundle in one `user` part with no
`systemInstruction` field; Codex receives the same merged string. A reply that
echoes the four markers because it was instructed to satisfies `verifyEcho`
identically to an honest one, and the ingestion floor is unaffected. The stated
invariant — payloads are data, never instructions — does not hold here, because
the material under review has to reach the model as text.

**On the proposed remedy.** Both reviewers suggested structural separation, a
system-instruction role or a separate part. Verification found this narrows the
surface and shifts the model's prior, but is trained behaviour rather than an
enforced boundary: no shipped API guarantees a model will not follow instructions
found in text labelled as data. It makes the boundary clearer; it does not
prevent compliance. Adopting it and claiming the problem solved would replace a
known gap with a hidden one.

**Outcome — fix the half that can be fixed, record the half that cannot.** The
payload's delimiters now carry the bundle's own end nonce, which is generated
fresh per bundle and therefore cannot appear in code that already exists. Bundle
content can no longer forge the closing delimiter, so the reviewer can always
tell where the material ends. That removes the impersonation half. It does not
stop a model obeying an instruction inside the bundle, and nothing available
does; that is recorded as a known limit, and the invariant's claim is corrected
where it is stated, rather than left reading as though it holds.

### codex-4 — an interior nonce satisfies the tail requirement — holds in part

**Checked by execution.** The claim's bundle was built outside the repository and
`bundleMarkers` run against it: `finalSection` came back `early.ts`, exactly as
predicted, because the section scan stops at the nonce's index.

**Holds:** the code checks only that a nonce exists, never that it is last, and
nothing rejects a second nonce-shaped line.

**Holds in part:** the last-line and uniqueness checks the finding asks for are
already specified — in `review-request`'s markdown, as commands an operator runs
and reads. They are prose, not an executable gate, which is the same defect in a
different place. Exploiting the gap also requires whoever generates the bundle,
who does not need the bypass to fabricate a result.

**Outcome — fix.** The checks become executable: `bundleMarkers` requires the
nonce on the last non-empty line and refuses a bundle carrying more than one
nonce-shaped line. A guard an operator has to remember to run is not a guard.

### codex-5 — a failed post-run credential read still publishes evidence — holds in part

**Holds:** the fail-open path is real and directly tested. When the post-run
credential cannot be read or parsed, no refreshed secrets are returned, the run
continues, and the scan searches only the credentials copied in before the run.

**Does not hold:** the premise that a refreshed token could be in the evidence.
Every writer of the three evidence files was traced: the manifest is built by the
runner from its own recorded facts, the session log is the filtered rollout, and
the reply is the model's text. None carries the contents of the credential file.
The subprocess's sandbox blocks file reads, measured on the only platform the
Codex family is permitted to run on.

**Outcome — known limit, not a fix.** The remedy the finding proposes is to
withhold evidence when the post-run credential cannot be read. That contradicts a
rule this design already holds: a run that caused egress leaves evidence that it
did. Trading a visible record of a real egress against an unreachable leak is the
wrong trade. Recorded in `docs/decisions.md` with the reachability analysis, so a
later change that makes the path reachable finds the note waiting.

### codex-6 — an arity assertion proves nothing — holds in part

**Holds:** `expect(geminiRequest.length).toBe(1)` sits under a test named for URL
safety and would pass against an implementation that built its URL by
concatenation. No secret is supplied to the builder in that test, so it cannot
demonstrate secret handling either. This is the prompt's own item 2 — a check
that passes regardless of the code under test — found in this branch's tests.

**Holds in part:** a sibling assertion does check the URL's content, including
that it contains no `?`, which structurally prevents a query string. Deleting the
arity assertion removes no coverage.

**Outcome — fix.** The arity assertion is replaced by assertions on what the test
claims to be about: the URL's actual value, and a sentinel credential's absence
from the built request when one is supplied.

### gemini-1 — a future-dated artifact pair wins the date sort — holds in part

**Checked by execution.** `findUnitArtifacts` was run against a synthetic list
containing a `9999-12-31` pair; it selected that pair.

**Holds:** selection is by newest date with no upper bound, and nothing refuses
when several pairs exist for one unit.

**Does not hold as framed:** "an attacker can easily bypass the review by
committing a dummy pair" understates the bar. The runner refuses unless both
files are tracked, unmodified, and their commit is an ancestor of the branch's
pushed upstream. That requires push access to the upstream — the same access
needed to change the source under review directly. It is missing defence in
depth, not an escalation path.

**Outcome — fix for visibility, and a recorded limit.** Refusing on multiple
pairs was considered and rejected: units are legitimately re-bundled (P5 was),
old artifacts are tracked records that must not be deleted to unblock a run, and
a test documents newest-wins as intended. Changing it would be an amendment, not
a review fix. Instead the runner reports how many pairs matched and which it
chose, and records both in the manifest, so a silent selection becomes a stated
one.

### gemini-2 — the bundle generator silently drops git-quoted filenames — holds

**Checked by execution**, in a throwaway repository outside this one.

**Found:** confirmed exactly. `git diff --name-only` wraps unusual paths in
quotes with escapes — `"caf\303\251.ts"` — and the generator's `[ -f "$f" ]` test
fails against that literal string, so the loop skips the file. The file's
contents never reach the bundle, no warning is printed, and the exit status stays
zero. `core.quotePath` is at its default in this repository, so the behaviour is
live here and needs no unusual configuration.

This is the most serious finding of the ten, and it is the only one that removes
code from review without anyone noticing. None of the generator's confirmation
checks would catch it: they test for excluded sections and for the nonce, and
nothing compares the bundle's contents against the diff it was built from. A file
that is simply absent raises nothing anywhere.

**Outcome — fix.** The generator reads null-delimited paths, which handles every
filename git can produce, and gains a confirmation check that the number of
sections in the bundle equals the number of files in the diff it was built from —
so any future omission, from any cause, fails the check instead of passing
silently.

### gemini-3 — suffix-only matching misses a leaked prefix — holds in part

**Holds:** the matcher compares the full value or its last 20 characters, so a
leak that reproduces a credential's first half and stops short is not detected.

**Does not hold:** the proposed remedy. Matching the leading characters as well
would reintroduce exactly the collision this rule was written to avoid —
`sk-proj-`, `sk-ant-a` and `eyJhbGci` are identical across every key of their
type, and a reply merely quoting such a placeholder would withhold all evidence
of a run whose bundle had already been sent. A test asserts that shared-prefix
values do not trip.

**Outcome — fix, by a different route than proposed.** A slice taken from the
middle of a long credential is unique to that credential and clear of both the
shared prefix and the tail. The matcher now checks the full value, its tail, and
that middle slice, which catches the prefix-truncated leak without reintroducing
the false positives. The finding was right that a gap exists and wrong about how
to close it; both are recorded.

## What this says about the reviewers

Ten findings, none rejected, six overstated in the same direction: each assumed
an actor holding access the design does not grant — a vendor that forges its own
telemetry, a model that knows a key it never receives, a contributor who can push
to the upstream. The mechanisms they described were real every time. The
consequences needed checking every time.

Both families raised the prompt-injection mechanism independently, and that is
the finding that is least fixable. The one confirmed defect that silently removes
code from review — the bundle generator's quoting — was raised by one family
only, and by the family that produced the shorter review. Corroboration sorted it
last; verification sorted it first.
