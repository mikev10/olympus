CONTEXT YOU NEED

This project runs AI coding agents (here, the Claude Code CLI) inside
disposable Docker containers.

Before this change, the model API key reached the CLI as an environment
variable on the command that ran it. Any process in the container could read
the key from its own environment, from /proc, or from a file the CLI wrote.

This change moves the key into a "model relay", a separate container that the
provider starts beside a sandbox and destroys with it:
- The relay sits on the sandbox's internal Docker network, which has no
  default route.
- The CLI is pointed at the relay and sends a placeholder where the key would
  go.
- The relay removes every authentication header the client sent and writes the
  real key into one named header.
- It forwards only requests whose path falls under a granted set of prefixes,
  to one fixed https origin, over verified TLS.
- A relay can be combined with either egress mode:
  - `deny-all`: the internal network carries the relay alone.
  - `allowlist`: the internal network also carries a filtering forward proxy,
    and the relay is added to NO_PROXY.

The driver no longer holds a credential. The conformance registry replays an
earlier exploit against a real task: a hook inside the container searches for
the key. Beside it runs a control, in which the key is passed the old way, to
show that the search can find it.

The bundle's commit range covers everything not yet externally reviewed. The
relay is the bulk of it. A smaller earlier change to the CI workflow, which
controls how often the model-calling tests run, is also in range and equally
in scope.

It must hold against a capable, motivated party who is trying to do any of
three things:
- read the credential's value from inside the sandbox
- use the credential for requests other than the granted paths on the granted
  origin
- make the assertions report the credential absent while it is in fact
  readable
Assume no deceptive intent, only that the easiest path gets taken.

WHO CONTROLS WHAT

That party controls everything running inside the sandbox container:
- the processes it starts, including hooks and children of the CLI
- the commands it runs and later execs into the container
- its environment and its filesystem
- the contents of the mounted workspace
- every byte of every request it sends to the relay: request line, method,
  path, query, headers, and body

It does not control any of the following:
- the `SandboxSpec` handed to the provider
- the credential values the provider is constructed with
- the Docker daemon, the host, and the provider's own Node process
- the programs the relay and proxy containers run
- the real upstream API origin

Those are runtime-selected and trusted, even where a function takes one as an
argument. The party also does not control code running inside the runtime's own
process.

The invariants at stake:

- Default deny. A capability not granted in policy is not available. A
  credential the task can read is a capability no policy granted, and so is a
  request the credential authenticates beyond the granted paths.

- Fail closed. A missing required check, an absent capability, an unsupported
  configuration, or a control that cannot be enforced is a refusal. It is never
  a silent degrade, and never a warning that lets the run continue. Here that
  covers four cases: a relay naming a credential the provider was not given; an
  upstream that is not an https origin; an empty path grant; and a provider
  that cannot keep a secret off the host.

- No agent writes to the project's Vault, which is its record of specs,
  evidence, and run state. This is enforced at the mount layer: at most one
  read-write mount, and if there is one it is the workspace. The relay must add
  no mount.

- Every capability claim maps to an executable assertion that fails when the
  capability is deleted. An assertion that would pass with the mechanism
  removed, or a scan that reports "found nothing" because it looked nowhere, is
  not evidence.

The mechanisms that matter most:

- The relay's request handling, which covers:
  - how the path is matched against the granted prefixes
  - which client headers are discarded and which are forwarded
  - how `Host` and absolute-form targets are treated
  - that redirects are not followed
  - how the upstream's TLS is verified
- How the credential reaches the relay container and nowhere else: the
  `docker run` argument vector, the environment of the `docker` process, what
  `docker inspect` of each container shows, and what the provider records as
  its applied controls.
- The network construction. Under both egress modes, it should leave the relay
  as the sandbox's only route to the model's API host, and the relay should be
  torn down with the sandbox, including when provisioning fails part-way.
- The exploit-replay assertion and its control. They cover what the scan reads
  (environments, /proc, files, docker inspect), and whether the control
  actually proves the scan can see what it reports absent.
