### Findings

1. **`packages/drivers/claude-code/src/driver.ts:558-560`; `packages/sandbox/src/local/provider.ts:176-216,377-395`; `packages/drivers/claude-code/test/driver.test.ts:156-163` — factually wrong — high** — The credential protection enforces **"not in argv," not "not readable by the model or another process."** `ANTHROPIC_API_KEY` is deliberately put in the Claude process environment. A Bash-enabled task runs as the same container UID and can read environment state; the straightforward construction is to inspect `/proc/*/environ` for `ANTHROPIC_API_KEY`. Even if Claude happened to scrub the environment inherited by a Bash child, the credential-bearing Claude process itself is still visible to same-UID processes unless an additional isolation mechanism outside this source prevents it. The test at `driver.test.ts:156-163` is effectively tautological for the stronger property: it asserts that the secret **is** in `ExecOptions.env` and only that it isn't in argv. **Resolve:** keep the model API credential out of the model-running container/process entirely, e.g. authenticate at a trusted egress/token-broker layer. A weaker alternative requires separate UIDs/process isolation, hidden `/proc`, and proven child-environment scrubbing. **Confidence: high.** The only thing I would check to reduce this finding is an external OS/CLI isolation guarantee not present in the supplied source.

2. **`packages/drivers/claude-code/src/driver.ts:290-317,511-551,574-605`; `packages/drivers/claude-code/src/stream.ts:18-29,64-77` — factually wrong — high** — The CLI tells the driver what tools actually exist in `init.tools`, but `runTask()` never compares that list with `req.tools`. It similarly does not validate the actual MCP server set, and `permissionDenials` are parsed but ignored. Concrete construction: request `['Read']`; have the invocation produce a perfectly valid stream whose init says `['Read','Bash']`; the driver returns a normal `TaskResult`. The property has already been violated before the model chooses whether to use Bash. The inverse also fails open: if the request grants `Read` but init contains no `Read`, the missing required capability is accepted. This is especially important because it is the natural backstop for every assumption about `--tools`, `--disallowedTools`, settings, and MCP behavior. **Resolve:** after init, require exact agreement between granted and actual tool/server inventory, with explicit normalization rules; reject extra and missing entries. Under `bypassPermissions`, a non-empty `permissionDenials` should also trigger a refusal unless there is a documented permitted case. **Confidence: high.**

3. **`packages/drivers/claude-code/src/driver.ts:137-141,511-551,722-736`; `packages/drivers/claude-code/test/claims.test.ts:57-98` — factually wrong — high** — A workspace-writable file is being used as trusted execution configuration. The hooks conformance test explicitly sets `settingsPath` to `/workspace/.claude/settings.json`; the driver later passes that same path with `--settings`. The workspace is untrusted by the framing. A task with Write/Edit/Bash can therefore change a hook from `true` to an arbitrary command. A later task granted only `Read`, or even no command tool, loads that file and causes the hook command to execute outside the task's `--tools` grant. A `SessionStart` hook makes this particularly direct. It also creates an easy path to the credential from finding 1. **Resolve:** settings that affect execution must be runtime-owned and immutable to the agent: root-owned/read-only file, separate read-only mount, or trusted inline configuration. Never reload control configuration from the writable workspace. **Confidence: high.**

4. **`packages/drivers/claude-code/src/driver.ts:277-287,326-334`; `packages/sandbox/src/local/provider.ts:377-426` — factually wrong — high** — Serialization covers the foreground `provider.exec()` promise, not processes the previous task leaves behind. The sandbox explicitly declares `persistent: true`, and neither task completion nor `cancel()` kills descendants. Concrete construction: Task A has Bash and starts a fully detached process with stdin/stdout/stderr redirected; Claude exits and `docker exec` returns. Task B on the same handle has a narrower or empty grant. The surviving process can continue reading/writing the workspace and making whatever sandbox-permitted network calls Task A could initiate while Task B is running. That makes the previous task's capabilities available during the later task. **Resolve:** establish a per-task process boundary and kill/verify all descendants before releasing `#serialized`, or use a fresh execution/container namespace per task. `cancel()` needs the same property. **Confidence: high.**

5. **`packages/conformance/src/kit/run-report.ts:62-102`; `packages/conformance/src/kit/reconcile.ts:69-120`; `packages/drivers/claude-code/package.json:18-24` — factually wrong — high** — The report is not bound to the **source tree being evaluated**. `packageTreeHash()` hashes only the owning package directory. But the driver tests execute workspace dependencies including `@olympus-ai/sandbox` and `@olympus-ai/core`. Concrete construction: run the driver assertions against sandbox implementation A and get a passing report; then change `packages/sandbox/src/local/provider.ts` without changing the driver package. The driver package hash remains identical, so reconciliation accepts the old result against sandbox implementation B. For I1 this is especially direct because the assertion's property depends on the sandbox provider. Root configuration and lockfile changes are also outside the hash. **Resolve:** bind the report to the complete execution input closure, preferably a repository tree/commit plus dirty-content digest, or at minimum all transitive workspace dependencies, root configuration/lockfile, and runtime image identity. **Confidence: high.**

6. **`packages/conformance/src/kit/reporter.ts:59-82`; `packages/conformance/src/kit/run-report.ts:62-67` — factually wrong — high** — Hashing only **after** the tests can bless code that was never executed. The comment at `reporter.ts:76-77` says the opposite of what the implementation does. Concrete construction: a long real-model test starts and loads source A; while it runs, a developer edits the package to source B; the already-loaded A passes; `onTestRunEnd` hashes B and writes that hash. Reconciliation against B succeeds. This does not require deception; editing while a long test is running is ordinary development behavior. **Resolve:** record the input hash before test modules execute and again after the run, and refuse to produce a passing report unless both are identical. A wrapper around the test process is safer than an end-only reporter hook because it can hash before Vitest loads the test graph. **Confidence: high.**

7. **`packages/drivers/claude-code/test/invariants.test.ts:74-148`; `packages/conformance/src/registry/i4.ts:266-274`; `packages/drivers/claude-code/test/driver.test.ts:175-190` — factually wrong — high** — `I4.driver-tool-inventory-validated` does not actually test the driver's narrow/empty-grant mechanism. `sessionTools()` launches Claude directly through `h.provider.exec` and constructs its own correct `--tools` arguments. Concrete deletion test: remove `--tools` from `ClaudeCodeDriver.#invocationFor`. The registered I4 assertion can still pass: the unknown-tool refusal remains, its one all-tools driver call isn't inspected for its actual tool set, and the narrow/empty checks use the independent `sessionTools()` implementation that still supplies `--tools`. The ordinary unit tests at `driver.test.ts:175-190` would fail, but reconciliation only asks whether the **registered assertion ID** passed; a failing unrelated unit test does not turn that I4 assertion into failed evidence. This is exactly the "assertion passes when the property is deleted" failure I8 is intended to prevent. **Resolve:** make the external I4 assertion inspect `sessionFor(taskId).tools` from actual `driver.runTask()` calls for the narrow and empty cases. If model cost is a concern, split "CLI flag semantics" from "driver wires the flag" into separate assertions, but the registered enforcement assertion must traverse the driver's actual path. **Confidence: high.**

8. **`packages/drivers/claude-code/src/image.ts:20-27,68-103` — factually wrong — high** — The pinned image source is not actually bound to the image that tests run. The image tag contains only `CLI_VERSION`, and `ensureImage()` returns immediately whenever that tag already exists. Concrete construction: change `image/Dockerfile` or `BASE_IMAGE` while leaving Claude version `2.1.277`; a developer/CI daemon already holding `factory-claude-code:2.1.277` reuses the old image. Tests then run against old runtime bytes, while the reporter hashes the new driver package and blesses the result as current. The same happens with an accidentally retagged local image. **Resolve:** derive the tag from a content hash of Dockerfile + base digest + CLI version, or stamp those values into immutable image labels and validate them before reuse. Recording the actual image digest in the run report would close the reconciliation side too. **Confidence: high.**

9. **`packages/drivers/claude-code/src/driver.ts:438-470,473-501` — factually wrong — high** — The MCP inventory check and the actual run consume the same **mutable `/tmp` pathname in separate execs**. The comment says keeping it outside the workspace means "a file the agent could edit between tasks" is avoided, but both the agent's commands and the driver execute as the same `node` user, so `/tmp/mcp-…json` is writable by agent-created processes. Combine this with finding 4: a surviving process from Task A waits for the inspection to finish, rewrites the MCP config, and the real task loads a different server/tool set than the one used to compute `--disallowedTools`. **Resolve:** inspection and execution must be bound to the exact same immutable config bytes/digest. Store runtime config somewhere agent processes cannot modify, and remove the cross-task process leak. **Confidence: high.**

10. **`packages/drivers/claude-code/src/driver.ts:98-102,484-497` — factually wrong — high** — The statement "Nothing secret is in it" is unenforced and contradicted by the type. `McpServerConfig` explicitly allows an `env` record, and the whole server object is JSON-stringified into `/tmp/mcp-…json`. If an MCP server's env contains an API token, database password, etc., it is plaintext in a same-UID-readable file. A Bash task can enumerate `/tmp/mcp-*.json`. **Resolve:** either prohibit secrets in `McpServerConfig.env` at the contract level, or supply MCP credentials through a privileged mechanism inaccessible to the task/model; merely deleting the file later does not protect it during the task. **Confidence: high on the exposure; medium on current impact because the bundle does not show a secret-valued MCP `env` in current configuration.**

11. **`packages/conformance/src/kit/reporter.ts:10-15,52-83`; `packages/conformance/src/kit/reconcile.ts:91-120` — factually wrong — medium** — An interrupted test run does not invalidate the previous passing report. The only write occurs in `onTestRunEnd`. Concrete construction: a valid passing report exists; start another run; kill Vitest or the machine before the end hook; `.conformance/run.json` remains the old passing report. A subsequent registry evaluation cannot tell the current run was interrupted. The comment's promise that every failing run overwrites the last passing run is therefore only true for runs that reach the reporter's end callback. This becomes materially worse when combined with the incomplete tree hash in finding 5. **Resolve:** atomically remove or replace the old report with an `in-progress` marker before tests begin; only rename a completed passing/failing report into place at normal termination. Missing/in-progress must refuse. **Confidence: high. Severity is medium because an old pass against truly identical complete inputs would still be useful evidence; the current hash is not complete, however.**

12. **`packages/conformance/src/kit/vitest.ts:28-45`; `packages/conformance/src/kit/run-report.ts:104-107`; `packages/conformance/src/kit/reporter.ts:59-70`; `packages/conformance/src/kit/reconcile.ts:122-150` — factually wrong — medium** — Reconciliation proves "a passing test whose full name contains `[id]` existed in this file," not "the registered `invariantTest` assertion ran." The reporter extracts any bracketed ID from any Vitest full name. A regular tautology such as `test('[driver.hooks] coverage', () => {})`, or an unrelated test nested under a `describe('[driver.hooks]', …)`, is enough for reconciliation if it is in the registered file. The title/function registered by `invariantTest` is not bound to the report at all. **Resolve:** have `invariantTest` register structured assertion metadata with the reporter instead of deriving identity from display names; refuse duplicate IDs and reconcile the registry's ID/title/location against that structured registration. **Confidence: high.**

13. **`packages/drivers/claude-code/src/driver.ts:438-470`; `packages/drivers/claude-code/test/driver.test.ts:261-266` — unclear — medium** — MCP inspection only requires that *some* `init` was parsed. It ignores the inspection process's exit code, result, stderr, and `init.mcpServers[].status`. The test covers "no init at all," not "init emitted but inspection later fails/is killed/server is disconnected." If Claude can emit init while an MCP server is failed, connecting, or incompletely enumerated, the driver can derive a too-small disallow list and continue. **Resolve:** define a positive completion condition: all requested servers must appear in a connected state, every granted MCP tool must appear, and inspection must terminate in the expected successful state. Add tests for init+nonzero, init+timeout, disconnected server, and granted-tool-absent. **Confidence: medium.** I would check the pinned CLI's exact ordering contract for its init event versus MCP initialization to decide whether this becomes high or disappears.

14. **`packages/core/src/driver/contract.ts:30-40`; `packages/conformance/src/registry/i8.ts:59-76` — factually wrong — medium** — There is a TypeScript-specific declaration-merging escape around the claim-key equality assertion. `DriverCapabilities` and `SandboxCapabilities` are interfaces, so another compilation unit can module-augment them. The generated conformance fixture imports the core interface only in the conformance program. A driver-local `declare module '@olympus-ai/core' { interface DriverCapabilities { newThing: boolean } }` can therefore make `newThing` a valid capability in the driver's compilation without making it a key seen by the conformance compilation, leaving no `driver.newThing` registry entry. I found **no such augmentation currently present**, so this is an available escape hatch, not an existing hidden capability. **Resolve:** make capability shapes non-augmentable type aliases and/or validate the runtime keys of `capabilities()` against the registry's known set. **Confidence: high on TypeScript behavior and the structural gap.**

On the language-specific question more broadly, I did **not** find a production `any` escape in the changed driver/reconciliation path. The conspicuous `as unknown as` casts are in tests and are generally doing the right thing: deliberately crossing the type boundary to prove runtime checks still refuse malformed inputs. Likewise, the `state as ReportedTestState` cast in `run-report.ts:161` is preceded by an explicit runtime membership check, so I do not consider it a bypass.

### Mechanisms I assess as sound

The **no-host-fallback driver construction** is sound in the supplied source: `ClaudeCodeDriver` runtime-checks that a provider exists, and the task, MCP-inspection, MCP-config, and artifact commands I traced all go through `SandboxProvider.exec`; I found no hidden `spawn()`/host execution path in the driver itself. The local provider also rejects unknown handles rather than treating them as paths or container IDs.

The **argv handling** is sound for the narrower property it actually claims: the credential value is not placed in the Docker or Claude argv, environment names are validated, Docker is spawned with `shell:false`, and the `exec "$@"` construction prevents Claude arguments from being reinterpreted by the shell. That is good argv hygiene; it simply does not provide credential confidentiality from the container.

The **network substrate shown in this change** also has the right shape: deny-all uses Docker `network:none`, while allowlist mode describes an internal network without a default external route, with proxy environment variables being convenience rather than the security boundary. I did not have the unchanged proxy implementation in this bundle, so I cannot independently certify host matching inside that proxy, but I found no new driver path that deliberately bypasses the sandbox network.

The **basic reconciliation refusals** are also sound individually: missing report, wrong report version/package, changed bytes within the owning package, missing assertion ID, skipped/failed/pending assertion, and wrong test file all refuse rather than degrade. The problem is provenance around those checks: what bytes the hash covers, when the hash is taken, whether the current run reached completion, and whether the named test really is the registered assertion.

### Framing

The framing is largely right, but I would widen the adversarial question in two places.

For the driver, **"what tools does this Claude session expose?" is too narrow because the sandbox is persistent**. The stronger question is: *what processes and mutable control state from every previous task can still act while this task is running?* `--tools` can be perfectly correct and task-level default deny can still be false because an old process, workspace-backed hook, or mutable MCP configuration operates beside it.

For reconciliation, **"does the report hash match the current package?" is also too narrow**. The right question is: *does this report identify one completed execution of this exact assertion against the exact complete execution inputs that the registry is evaluating?* Today the answer is no because the hash omits dependency/runtime inputs, is taken only after execution, and is not tied to a current completed test invocation.

Those two reframings are the common thread in the highest-severity findings: the code has strong point checks, but several of them protect a narrower boundary than the property being claimed.
