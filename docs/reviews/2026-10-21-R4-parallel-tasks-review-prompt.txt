CONTEXT YOU NEED

The runtime carries a task graph through fixed stations. At `build`, a model
driver changes a copy of the repository in a sandbox; at `verify`, the runtime
collects that task's own diff, composes it over the change accepted so far, and
runs pinned checks over the result; a task whose checks pass is "accepted", and
the cumulative accepted diff is what is eventually merged. This change lets
`build` run every task whose dependencies have passed at the same time, up to a
limit, while `verify` stays one task at a time. When a path a task changed was
also changed by a sibling's work accepted after the task started, that is a
conflict: the task is rebuilt over the accepted tree, up to a policy bound, and
then parked; no side is ever picked and nothing is merged inside a file. State
lives in a versioned run-state record committed through a Vault, and every
refusal, park and conflict is written to an enforcement record.

It must hold against a capable, motivated party trying to get a change accepted
that silently discards or overwrites another task's accepted work, to run more
tasks at once than policy and the driver allow, or to make a task's status or
counts reflect something other than its own evidence. Assume no deceptive
intent — only that the easiest path gets taken.

That party controls what the model driver writes into each task's workspace and
what each driver call returns, how long each call takes, the order in which
concurrent calls finish, and when the process stops (it can be killed between
any two commits). It does not control the components the runtime is wired with
— the Vault, the sandbox provider, and the drivers are runtime-selected and
trusted, even where a function takes one as an argument — and it does not
control code running inside the runtime's own process, the policy file, the
task graph, or the check manifest, all of which were admitted and locked before
the run started.

The invariants at stake:

- Fail closed. A missing check, an absent capability, an unsupported stack, or
  a shrunken suite is a refusal — never a silent degrade, never a warning that
  lets the run continue. Here: a sibling's accepted change is never silently
  overwritten, and a conflict past its bound parks rather than picking a side.
- An agent may not be judged by an artifact it can write. Here: a task starts
  from the base plus accepted changes only, never from a sibling's unverified
  work.
- The runtime derives status; the model never reports it. Each task's status is
  derived from its own evidence, and no task's commit changes another's status
  or counts.
- Default deny. A capability not granted in policy is unavailable. Here:
  concurrency is never more than both the policy's `maxParallelTasks` and the
  driver's declared `parallelism` allow.
- Every capability claim maps to an executable assertion that fails when the
  capability is deleted. Here: the driver's declared `parallelism` is a number
  something enforces and an assertion checks.
