CONTEXT YOU NEED

The runtime carries a code change, written by a model agent, through a fixed
line of stations (intake, spec, test-design, plan, build, verify, review,
integrate, ...); the runtime, not the model, decides whether the change
advances. This change adds two deterministic security check kinds,
`secret-scan` (gitleaks) and `static-analysis` (Semgrep), each run by the
runtime in its own image pinned by digest, over a runtime-made copy of the
tree with no network, first over the base commit and then at `verify`. A
check fails only on a finding whose fingerprint (derived by the runtime, not
read from the scanner) the base's findings do not account for, or when the
diff adds a suppression marker. It also requires every spec to carry a
"security part" naming its authorization rules, refuses the test-design
station when a named rule has no check that exercises a denied caller, and
records each failed verify iteration in the enforcement record.

It must hold against a capable, motivated party trying to get a change that
commits a credential or adds a flagged code pattern through `verify` without
the check failing, or to keep the record from showing why it failed. Assume no
deceptive intent — only that the easiest path gets taken.

That party controls the agent's writes to the workspace during build: every
file in the tree, including scanner ignore and configuration files
(`.gitleaksignore`, `.gitleaks.toml`, `.semgrepignore`), file names, symlinks,
file contents and inline comments, and what the model's result claims it did.
Separately, the person or client submitting a run controls the request: the
check manifest, the spec and its security part, the task graph. It does not
control the components the runtime is wired with — the Vault, the sandbox
provider, the drivers, and the scanner set — which are runtime-selected and
trusted, even where a function takes one as an argument, and it does not
control code running inside the runtime's own process.

The invariants at stake:

- The runtime derives status; the model never reports it. A check passes or
  fails on what the runtime itself ran and read, never on the model's account.
- An agent may not be judged by an artifact it can write. The spec, the
  acceptance tests, and the check manifest are hashed and locked before build;
  nothing the agent writes may change how its change is judged.
- Default deny. A capability not granted in policy is unavailable; a security
  check's sandbox has no network.
- Fail closed. A missing check, missing capability, unsupported stack, an
  unreadable report, or a shrunken suite refuses; it never degrades silently
  or warns and continues.
- No agent writes to the Vault (the runtime's evidence store), and secrets
  found by a scan must not be stored in it.

The mechanisms that matter most:

- `scanTree` (packages/api/src/scan.ts): the copy of the tree with in-tree
  scanner files removed, the read-only rules mount, the pinned image, the

- Admission and station refusals: manifest validation of security checks
