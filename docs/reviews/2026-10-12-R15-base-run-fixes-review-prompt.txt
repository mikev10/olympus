CONTEXT YOU NEED

The runtime carries a change through fixed stations. At `test-design` it locks the acceptance tests and a verification manifest (a list of checks); at `verify` it runs those checks over the base plus the change, and a task passes only if its required checks pass. A check that already passes on the unchanged base would pass whatever the change did, so each acceptance check, and optionally each behavioral check, declares whether it 'fails' or 'passes' on the base; admission refuses a manifest with no required check declared 'fails'; every declared check runs over a fresh read-only copy of the base at the `test-design` exit before any model is invoked; the results are recorded once in a runtime-only store (the Vault); and the exit is refused when a check does not do what it declared, including when it ran fewer test suites than it requires.

The bundle covers a follow-up range on top of that gate, not the whole gate: code unchanged in this range is not shown. The range makes three changes. First, a `unit` or `acceptance` check no longer pins a command: the runtime starts the test framework the base declares, from the base's own install, with an argument vector the framework adapter builds (`runner`, `invocation`, `selectSuites`); an acceptance check names the locked tests it runs, and the suite count recorded is the number of those tests the runner is made to load. Admission refuses, against the base snapshot, a suite check that pins a command, a check of no known kind, a test name the runner would not select exactly, and a base with no runner installed where the adapter expects it. Second, what a task writes under any `node_modules` directory is not carried into the tree the checks run over at `verify`; it is recorded by package in the evidence (`notCarried`) and escalates the `integrate` exit to a human. Third, the local Vault refuses a base-run record whose result lacks a suite count or carries a non-integer exit code.

It must hold against a capable, motivated party trying to get a change accepted by a gate that never required the change: a suite check that reports suites it never ran, an acceptance check whose named tests select something other than what was named, a check whose judge — the test runner or anything it loads — was altered by the change it judges, or a run that crosses `test-design` without its base being judged. Assume no deceptive intent — only that the easiest path gets taken.

That party controls the verification manifest and the acceptance test files submitted with a run (their content, kinds, declarations, named tests, and any commands), the repository contents that make up the base (including its test-framework configuration and anything installed under it), every file the model writes during `build` (including under `node_modules`), and when the runtime process stops (a run may be resumed from any committed state). It does not control the components the runtime is wired with — the Vault, the sandbox provider, the workspace store, the framework adapters, and the drivers are runtime-selected and trusted, even where a function takes one as an argument — and it does not control code running inside the runtime's own process.

The invariants at stake:

- The runtime derives status; the model never reports it. Results are collected by the runtime from processes it ran; nothing a model returned, and nothing written by a process running the code under test, decides an outcome.
- An agent may not be judged by an artifact it can write. Specs and acceptance tests are hashed before build and re-verified at every station transition; the runner that judges a change must not be something that change could alter.
- Fail closed. A missing check, a check that did not start, an unsupported stack, a runner that is not installed, or a test suite that enumerates below what was expected is a refusal — never a silent degrade or a warning that lets the run continue.
- Default deny. A check sandbox has no network unless policy grants it.
- No agent writes to the Vault.
