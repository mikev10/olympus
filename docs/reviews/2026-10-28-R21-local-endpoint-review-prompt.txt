CONTEXT YOU NEED

The runtime runs an agent's task inside a Docker sandbox on an internal network
with no route out. The agent reaches its model only through a "relay": a
separate container the runtime starts, which holds the model credential,
forwards a granted set of paths to one fixed upstream, and meters and bounds
spending. Until this change the relay accepted only an `https` upstream and
refused to start without a credential. This change lets it reach a model
listening over plain `http` on the Docker host with no credential. That is
allowed only when the relay specification declares a local upstream as a
structure (`{ local: 'docker-host', port }`), declares no credential as `null`
together with a `'none'` scheme, and names a port the sandbox provider was
given by its operator (`dockerHostPorts`). The route is a host name
(`model-host`, mapped to the Docker host gateway) added to the relay container
alone. The OpenAI-compatible driver's configuration and the host's endpoint
file take the same declarations.

It must hold against a capable, motivated party trying to reach the Docker host
or an unauthenticated route out of the sandbox that the operator did not
declare. That includes making the relay speak plain `http` to somewhere other
than the declared host port, making it forward without a credential to a
remote origin, reaching the host's services from inside the sandbox, or getting
a key the task supplies to the endpoint. Assume no deceptive intent — only that
the easiest path gets taken.

That party controls everything the task does inside the sandbox: every process,
file, and request it makes to the relay, including headers and request targets.
A relay specification can also arrive from a driver's code, so assume it may be
malformed or not match its TypeScript type. The party does not control the
operator's configuration: the provider's `credentials` and `dockerHostPorts`,
or the endpoint file and environment the host reads. It also does not control
the components the runtime is wired with. The Vault, the sandbox provider, and
the drivers are runtime-selected and trusted, even where a function takes one
as an argument, and the party does not control code running inside the
runtime's own process.

The invariants at stake:

- Default deny. A capability not granted in policy or by the operator is
  unavailable. A route to the Docker host is a capability.
- Fail closed. A missing or malformed declaration is a refusal, never a silent
  degrade. In particular `http`, and the absence of a credential, are never
  inferred from a URL or from an absent or empty value.
- No agent reaches the model credential. It is held in the relay container and
  appears in no sandbox process, file, environment, or argument vector.
- Spending is metered and bounded by the relay for every upstream, local or
  not, exactly as for a remote one.

The mechanisms that matter most:

- `checkRelay` and `checkLocalUpstream` in `packages/sandbox/src/local/relay.ts`:
  the TypeScript-side validation of upstream, scheme, credential, and port.
- The start checks and `send` inside `RELAY_SOURCE`, the relay's own program:
  the second validation, the choice of `http` or `https`, and which headers
  reach the endpoint.
- `startRelay`'s argument vector: where `--add-host` and the credential
  variable are added, and on which container.
- `checkConfig`/`checkUpstream` in the driver, and `parseEndpointFile`,
  `endpointGrants`, and `main.ts` in the host: how a keyless local endpoint is
  read, and what the provider is given.
