CONTEXT YOU NEED

The runtime carries a change written by a model agent through fixed stations
and lets it advance only on checks the runtime runs itself. Until this change it
supported only TypeScript repositories (vitest or jest). This change adds a
Python adapter set: pytest test discovery, assertion, skip-marker, and test-case
reading done by parsing files on the host (TOML, INI, and Python parsed in
TypeScript, nothing executed); coverage read from coverage.py's JSON report;
Python config files treated as protected; and two dependency installers (uv for
`uv.lock`, pip for a hashed `requirements.txt`) that build a virtualenv with
copied binaries and install it in a sandbox, after which every check runs over
that install, read-only, with no network, in the same container image. It also
changes the installer contract from one argument vector to a list of steps.

It must hold against a capable, motivated party trying to make a Python change
pass the gate without the tests that judge it really passing — by weakening,
skipping, deleting, or hiding tests, by changing what the test runner collects
or loads, or by getting code of its own run as the judge. Assume no deceptive
intent — only that the easiest path gets taken.

That party controls every file of the repository's working tree the change
produces: test files, source files, conftest.py, pyproject.toml, setup.cfg,
pytest.ini, tox.ini, requirements files, uv.lock, and anything else it can write,
including files under directories named .venv, site-packages, or __pycache__. It
also controls what the base repository a run starts from contains, within what a
repository author could commit. It does not control the components the runtime
is wired with — the Vault, the sandbox provider, the container images pinned by
digest, the installer declarations, and the drivers are runtime-selected and
trusted, even where a function takes one as an argument — and it does not
control code running inside the runtime's own process. Package registries
(PyPI) are reached only by the install sandbox, and only to hosts a policy
grants.

The invariants at stake:

- An agent may not be judged by an artifact it can write. The tests and the
  runner that judge a change must be ones the change cannot alter; a change's
  writes into dependency trees are recorded and never carried into the tree the
  checks run over.
- Fail closed. A missing check, an absent capability, an unsupported stack, an
  unreadable config, or a shrunken suite is a refusal — never a silent degrade
  and never a warning that lets the run continue.
- Nothing an adapter does runs repository code on the host: configs and tests
  are parsed, never loaded or executed.
- The runtime derives status; a test runner's own output is not trusted to say
  how many tests exist.

The mechanisms that matter most:

- Static pytest collection (`packages/adapters/src/python/discovery.ts`,
  `config.ts`, `ini.ts`): which files and cases the host believes pytest will
  collect, and what config or conftest content is refused.
- Assertion, skip-marker, and case reading (`python/tests.ts`), which tamper
  analysis compares between the tree a change was handed and the tree it left.
- The installers and lockfile readers (`python/install.ts`) and the runtime's
  multi-step install (`packages/api/src/install.ts`): what may reach the
  virtualenv a check then trusts as its runner.
- Dependency-tree handling and the check image (`packages/adapters/src/trees.ts`,
  `packages/api/src/workspace.ts`, `line.ts`, `verification.ts`).
