CONTEXT YOU NEED

The runtime drives agent-written code through a fixed line of stations. Until this change, every run was started by a person, and the trigger section of the policy was validated but read by nothing. This change makes admission read the trigger policy for every run, a person's included, and adds one outside path: `POST /events/<subscription>` accepts a webhook delivery that a subscription in policy grants. The delivery is verified by an HMAC under a secret the host holds, reduced to a few fields a per-kind schema in code bounds, and recorded in the Vault as an intake candidate. Nothing runs from a candidate until a person admits a run from it through the authenticated API, writing the run's intent themselves. A daily schedule records candidates the same way. Code lives in `packages/core/src/trigger/` and the policy validator, `packages/triggers/src/` (signature and GitHub extractor), the Vault's intake store (`packages/vault/src/`), `packages/api/src/intake.ts`, `schedule.ts`, `run.ts`, `http/server.ts`, and the host. A type-aware ESLint rule lives in `packages/conformance/lint/untrusted-sink.js`, and the conformance assertions are in `packages/conformance/src/registry/triggers.ts`.

It must hold against a capable, motivated party trying to get its text in front of a model, to start or shape a run it was not granted, or to make the line act on an event the policy does not admit — and against a conformance suite that would pass while any of that holds. Assume no deceptive intent — only that the easiest path gets taken.

That party controls the bytes of any HTTP request sent to the events route: its path, headers, and body, including a body it captured from a real delivery and sends again, late or repeatedly. It controls the content of GitHub objects a real signed delivery describes — an issue's title, body, and labels, a branch name, a check's name, an author association it holds — but not the subscription's secret. It controls the code an agent writes in a workspace. It does not control the components the runtime is wired with — the Vault, the sandbox provider, and the drivers are runtime-selected and trusted, even where a function takes one as an argument — and it does not control code running inside the runtime's own process, the policy file, the host's environment, or the person holding the local API token.

The invariants at stake:

- Event payloads are data, never instructions. Untrusted text enters inside an envelope (`UntrustedPayload`, whose `raw` is an opaque `UntrustedText`) and is never concatenated into a system or role prompt. Triggers select pre-declared templates; payloads supply parameters only. Only a trigger extractor may read `raw`.
- Default deny. A capability not granted in policy is unavailable: a delivery for a subscription the policy does not name is refused before its body is read.
- Fail closed. A missing check, a missing timestamp, an unverified signature, an over-cap value, or an exhausted budget is a refusal — never a silent degrade, a truncation, a clamp, or a warning that lets the run continue. A requested autonomy level above a cap is refused, never lowered.
- The runtime derives status; the model and the payload never report it. Expiry and the budget window run on the runtime's clock.
- No agent writes to the Vault. Candidates and decisions are written by the host runtime only.

The mechanisms that matter most:

- The delivery pipeline in `api/src/intake.ts` and `http/server.ts`: the order of the subscription check, the byte cap, the constant-time HMAC check, the replay check on the body's SHA-256 (stored in the same write as the outcome), the staleness check on the body's own timestamp, and the budget.
- The GitHub extractor (`triggers/src/github.ts`) and `checkFields` with `FIELD_SCHEMAS` and `CHAR_CLASSES` (`core/src/trigger/schemas.ts`): whether anything other than bounded, non-free-text fields can leave a payload.
- Admission (`core/src/trigger/admission.ts`, `api/src/run.ts`): the trigger checks for every kind, admission from a candidate exactly once, expiry, and the relational policy validation in `core/src/policy/validation.ts`.
- The sink lint rule and the conformance assertions that claim to prove each of the above.
