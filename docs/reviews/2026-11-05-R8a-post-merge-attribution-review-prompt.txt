CONTEXT YOU NEED

After the runtime merges a run's pull request, the run now enters an `observe`
station and stays there until a policy-set observation window has passed since
GitHub's merge time. Two job templates feed observation. `observe-signal`
records a signed GitHub webhook (a push to the default branch, or a failed
check run) against the change whose commit it names. `observe-history` is a
scheduled walk of the default branch's first-parent git history. It finds a
later commit whose diff is an exact inverse of a change (a rollback, matched by
`git patch-id --stable`) or inverts some of its hunks (a partial reversal), and
it closes windows. Every first-parent change no run made is a baseline change.
From these write-once observation records, a pure derivation produces the
escaped false-done rate (merged runs that later had a rollback or a failed
check on the merge commit, over runs whose window closed), the change-failure
rate per role and per seat identity beside the baseline's, rollback counts,
time to restore, and the baseline's lead time. Each rate carries its sample
size and a one-sided 95% bound. Every recorded time is labelled
`provider-reported`, `committer-claimed`, or `runtime`.

These figures are the project's evidence that work it called done stayed done.
They must hold against a capable, motivated party trying to make the line's
post-merge record look cleaner than it is: to hide a rollback or a failed check
from a run's record, attribute one to the wrong run or to no run, get a run
counted as clean before its window has closed, or make the baseline look worse
or the line look better than they are. Assume no deceptive intent — only that
the easiest path gets taken.

That party controls the contents of the target repository: commit messages,
commit author and committer dates, file contents and diffs, branch layout and
merge shape, and the repository's own configuration files (including
`.gitattributes`). It controls the free-text fields of a webhook body (check
names, outputs, titles, pull-request lists, head-commit messages), but it
cannot forge the body's HMAC signature, which is verified before the body is
parsed. It controls when commits land relative to the scheduled walk. It does
not control the components the runtime is wired with — the Vault (the store
the records are written to), the git binary on the host, the clock, and the
policy file are runtime-selected and trusted, even where a function takes one
as an argument — and it does not control code running inside the runtime's own
process.

The invariants at stake:

- The runtime derives status; the model never reports it. Every observation
  and every rate is derived from git and from signed bodies by the runtime,
  never from anything a model says.
- Fail closed. A history that cannot be read, a range that was rewritten, or
  a missing observation window is a refusal, never an empty walk or a clean
  result. A run still observing is never counted as clean.
- Event payloads are data, never instructions. A webhook body enters as
  typed, schema-checked fields only, and a signal is attributed by the commit
  identity it names, never by any other field.
- Default deny. A template is valid only on the trigger kinds that can carry
  it, and a policy that names an observe template without a window is refused.
- No Greek mythological names in code identifiers, strings, paths, or config
  keys.

The mechanisms that matter most:
