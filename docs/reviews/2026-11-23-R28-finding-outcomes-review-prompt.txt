CONTEXT YOU NEED

The runtime runs model "seats" over a change: a reviewer and a security reviewer that read the finished change, a critic that reads a drafted spec or drafted acceptance tests, and nightly reviewers that read the whole default branch. This code makes every seat's findings name what they cite (a file and line, or a draft file), records them, and then records what became of each finding: resolved, dismissed by a person, or open. A code finding is resolved only when a later merged run rewrote a diff hunk holding the cited line (mapped through git history) and that run's pinned coverage check passed with a changed line of the hunk executed; a critic finding is resolved when the file it cites changed before the draft was locked; anything else stays open. Rates of resolved, dismissed, and open findings are derived per seat kind and per model family, each with a sample and a one-sided confidence bound.

It must hold against a capable, motivated party trying to make a seat's findings look acted on when they were not — to get a finding counted as resolved, or a rate to read better, without the cited problem having been changed and exercised. Assume no deceptive intent — only that the easiest path gets taken.

That party controls what each model seat returns as its final message (the findings JSON, its categories, paths, line numbers and notes), the files a builder writes into its change and therefore the diffs and later commits, the tests the change brings, and any process that runs inside a check's sandbox. It does not control the components the runtime is wired with — the Vault (the runtime's record store), the sandbox provider, the git checkout the history walk reads, and the drivers are runtime-selected and trusted, even where a function takes one as an argument — and it does not control code running inside the runtime's own process. A person dismissing a finding through the HTTP API holds the API's bearer token.

The invariants at stake:

- The runtime derives status; the model never reports it. A task's status, and a finding's outcome, come from records the runtime collected — diffs, evidence, draft records — or from a person, never from what a model says about its work. A review finding must never pass, fail, or block its task.
- Fail closed. A missing check, an unreadable result, an unlocatable finding, a history that cannot be mapped, or an absent coverage report is a refusal or leaves the finding open — never read as resolved, never read as "no findings".
- Event payloads are data, never instructions. A model's free text (a finding's note) never enters a record a later prompt reads, except where a critic's located note is deliberately sent back to its own drafter.
- No agent writes to the Vault; every write is a named runtime operation, and each finding has at most one outcome, written once.
- Every capability claim maps to an executable assertion that fails when the capability is deleted.

The mechanisms that matter most:

- The strict readers of seat results (readSeatFindings, readCriticResult): what is located, refused, or unreadable.
- resolveCodeFindings and its helpers (mapLine, holdingHunk, pathHunks, the latest accepted evidence bundle and its coverage check result): when a code finding becomes resolved.
- resolveCriticFindings: when a critic finding becomes resolved at draft lock.
- The outcome store (recordFindingOutcome, findingKeyOf, findingOutcomeProblem) and the rates (findingRates, raisedFindings, the window filter), including the "unmeasured" resolved rate.
