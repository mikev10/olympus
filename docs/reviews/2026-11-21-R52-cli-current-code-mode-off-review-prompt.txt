CONTEXT YOU NEED

The driver builds a container image holding the Claude Code CLI at one pinned version, then runs each task as a CLI session inside a sandbox, with the tools the task's policy granted passed as `--tools` and every other configuration source turned off. This change moves the pinned CLI from 2.1.310 to 2.1.330, a release line that fixes permission-check bypasses in the CLI. It also switches off the CLI's "Code Mode", an experimental feature added in 2.1.323. In Code Mode the model writes JavaScript that calls its tools through a script tool (`REPL`), rather than calling each tool individually. The switch is the environment variable `CLAUDE_CODE_EXPERIMENTAL_CODE_MODE`, set to `0` on every exec the driver makes. The vendor documents `1` as on and `0` as off, and says a `0` in the environment or a settings file keeps the feature off even where the other says `1`. The bundle also carries maintainer tooling and documentation commits that landed in the same range; those are reviewable but are not the subject.

It must hold against a capable, motivated party trying to reach a tool, or a way of calling tools, that the task's policy did not grant. Assume no deceptive intent — only
that the easiest path gets taken.

That party controls what the model returns, every command and file write the granted tools let it make inside the container, the files in the workspace, and anything it can write in the container's own filesystem, the CLI's home directory under /tmp included. It does not control the components the runtime is wired with — the Vault, the sandbox
provider, and the drivers are runtime-selected and trusted, even where a
function takes one as an argument — and it does not control code running inside
the runtime's own process. In particular it does not choose the argv or the environment the driver passes to `docker exec`, and it does not choose the CLI version the image is built from.

The invariants at stake:

Default deny: a capability not granted in policy is not available. Adding one is an explicit, versioned edit to policy. A tool the grant did not name must be unavailable to the model, not merely unused.

Fail closed: a missing required check, an absent driver capability, an unsupported stack, or a shrunken suite is a refusal — never a silent degrade, never a warning that lets the run continue.

Every capability claim maps to an executable assertion that fails when the capability is deleted. Documentation asserting a subsystem is wired is not evidence that it is.

The mechanisms that matter most:

- `CLI_ENVIRONMENT` in `src/driver.ts`, the base environment of every exec, now carrying `CLAUDE_CODE_EXPERIMENTAL_CODE_MODE: '0'`, and `environmentFor`, which layers per-model settings over it.
- The two CLI invocations that inherit it: the MCP inspection (`#ungrantedMcpTools`) and the task run (`#invocationFor`), including the optional `--settings` file.
- `CLI_VERSION` in `src/image.ts`, from which the image tag and the Dockerfile build argument are both derived.
- The new tests in `test/driver.test.ts` ("Code Mode is off in every session the driver starts") and the added `REPL` refusal in `test/invariants.test.ts`, which are meant to fail when the switch is deleted or set to `1`.
