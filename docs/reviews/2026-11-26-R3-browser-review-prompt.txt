CONTEXT YOU NEED

The project runs code written by an AI agent inside a Docker container (the
sandbox) and decides, in its own host process (the runtime), whether that code
does what a locked acceptance scenario says. This change adds a browser
scenario. The scenario's `serve` command starts the agent's web product inside
the sandbox. A second container, started from a pinned browser image, joins the
sandbox's network namespace and nothing else of it, carries out the scenario's
steps against the sandbox's loopback, and prints what was on the page. The
adapter, on the host, compares that report with the scenario's expectation and
returns the verdict.

It must hold against a capable, motivated party trying to have a browser
scenario pass on a page that does not show what the scenario expects, or pass
without the page having been exercised. Assume no deceptive intent — only
that the easiest path gets taken.

That party controls everything inside the sandbox container: the web product,
every byte of HTML, CSS, and script it serves, every other process there, and
anything those processes can do on the network namespace they share with the
browser's container, including connecting to any port listening on its
loopback. It does not control the scenario: its steps, its expectation, and its
`mayBlock` list are locked before the product is written, and the party cannot
edit them. It does not control the components the runtime is wired with — the
Vault, the sandbox provider, and the drivers are runtime-selected and trusted,
even where a function takes one as an argument — and it does not control code
running inside the runtime's own process. It does not control the Docker
daemon, the pinned browser image, or the program the provider writes to the
browser container's standard input.

The invariants at stake:

- The runtime derives the verdict; the product never reports it. What the
  browser prints is an observation, and the comparison that decides pass or
  fail runs on the host.
- An agent may not be judged by an artifact it can write. The browser that
  observes the product must be out of the product's reach, and a scenario names
  elements by what a person sees (a role and accessible name, a label, visible
  text), never by markup the agent chooses.
- Default deny. A capability not granted is unavailable. A browse request names
  a port and never a host, and the browser reaches the sandbox's loopback and
  nothing else.
- Fail closed. A provider that cannot browse is named as lacking the control. A
  host the page asked for and could not reach fails the scenario unless the
  locked scenario lists it. A step that could not be done is never read as
  done. A missing or malformed report is never read as a pass.
- Every capability claim maps to an executable assertion that fails when the
  capability is deleted.

The mechanisms that matter most:

- `browseRunArgs` and `LocalDockerProvider.browse`: how the browser's container
  is started, what it shares with the sandbox, and how its lifetime is tied to
  the sandbox's wall clock.
- The program in `browse-source.ts`, which runs inside the browser's container:
  two listeners that refuse every request not sent to the loopback, Chrome
  driven over a pipe, elements found and read in a script world separate from
  the page's, and the report it prints.
- `readBrowseOutput`, which reads that report on the host, and
  `readBrowserScenario` and `compareBrowser`, which read the scenario and
  decide the verdict.
- The seven registry assertions in
  `packages/conformance/src/registry/browser.ts`, and the three existing ones
  that were reworded.
