CONTEXT YOU NEED

The project is a runtime that carries a software change through a fixed line of
stations (build, verify, review, integrate, and others). Each station runs
model-driven tasks in a fresh sandbox, under a role whose capability (tools,
network egress, autonomy level, writable paths) comes from a policy. This unit
adds narrowing. A run whose triggering author has low trust, or that seats a
role granted a sensitive path class, is narrowed at admission. A run that later
receives input from a declared source is narrowed before that input reaches a
model. Once narrowed, every later task's sandbox egress, tools, and exit
approval level come from each role's narrowed scope, and nothing in the run
restores them. Paths in a sensitive class are left out of every tree a model is
handed, unless its role is granted the class in a run narrowed at admission. A
task that writes such a path is refused.

It must hold against a capable, motivated party trying to obtain, inside a run,
a capability wider than the narrowing allows: reach a host, use a tool, read a
sensitive file, or pass an exit at a level above the narrowed one. The same
holds for getting narrowing input in front of a model before the narrowing is
in force, or replacing a sensitive file unseen. Assume no deceptive intent —
only that the easiest path gets taken.

That party controls what a model returns and does in its sandbox: the files it
writes to its workspace, the result it reports, and when it fails. It also
controls the text of input a declared source brings, and the author trust and
content of an event that becomes a run. It does not control the policy document,
which a person writes, or the components the runtime is wired with — the Vault
(the record store), the sandbox provider, and the drivers are runtime-selected
and trusted, even where a function takes one as an argument. It does not control
code running inside the runtime's own process, including the hook through which
the runtime's own input sources reach the line.

The invariants at stake:

- Default deny. A capability not granted in policy is unavailable. A narrowed
  scope can only take capability away.
- Fail closed. A missing check, a missing capability, or a step that cannot
  complete is a refusal, never a silent degrade or a warn-and-continue. An
  over-request is refused, never quietly lowered.
- The runtime derives status; the model never reports it. Narrowing is decided
  by the runtime from the admitted trigger, policy, and declared sources, never
  from anything a model returned.
- Event payloads are data, never instructions. Untrusted text is never
  concatenated into a system or role prompt.
- Every capability claim maps to an executable assertion that fails when the
  capability is deleted.

The mechanisms that matter most:

- Admission narrowing (`narrowAtAdmission`, `planNarrowing`, and their caller in
  `run.ts`). It refuses a narrowed run that seats a role with no narrowed scope,
  or that asks a level above a narrowed ceiling, and records the narrowing
  before the first run state.
- The line's narrowed scope (`scopeFor`, `narrowedScope`, `levelOf`, and every
  site that reads the run's level). Each task's sandbox, tools, and exit level
  come from these.
- `narrowRun` and `WithheldInput`. Input is recorded, then committed, then
  released, and `runTask` places only released input, and only in a narrowed
  run. Run state's `narrowed` is kept over any later change.
- Sensitive paths (`withheldGlobs`, `omitWithheld`, `omitPaths`, and the write
  refusal in `verify`). Omission covers the build, review, drafter, and critic
  trees, while verification runs over the full tree.
