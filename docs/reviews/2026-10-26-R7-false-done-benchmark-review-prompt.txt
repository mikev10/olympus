CONTEXT YOU NEED

The runtime carries AI-written work through a fixed line of stations (spec,
test design, build, verify, review, integrate) and decides from its own checks,
never from the agent's word, whether the work is done. This change adds
`packages/benchmark` and a pinned corpus under `corpus/v1/`. Each corpus item
is either seeded (a change that looks done but is not: a skipped test, a
weakened assertion, an edited locked acceptance test, a leaked credential, a
write outside the files the builder may touch, a drafted spec or test that
misses its intent) or a control (a similar change that is sound). The
benchmark runs every item and publishes, per arm and per group, a detection
rate over seeded items and a false-refusal rate over controls, each with a
one-sided 95% Clopper–Pearson bound.

There are two tiers. The deterministic tier puts a scripted seat on the real
line (real vault, real Docker sandbox, real scanners), which applies the item's
change and claims done; CI reruns it and requires the result to match the
committed `docs/benchmark/v1-deterministic.json` byte for byte. The model tier
runs once, under a spending cap: a real model as the critic of drafted items,
and the same model alone, asked to answer strict JSON on whether the work is
done. Its result is committed as `docs/benchmark/v1-model.json`. A small change
to `packages/api` exports the meter binding the line uses, so the benchmark's
model calls are metered the same way.

It must hold against a capable, motivated party trying to make the published
numbers better than the line's controls and the model actually earned — a
detection rate that counts a catch nobody made, or a false-refusal rate that
hides a refusal. Assume no deceptive intent — only that the easiest path gets
taken.

That party controls what the model returns (the alone arm's verdict text, the
critic's findings), the files the seat writes in its workspace, and when a run
stops or throws. It does not control the components the runtime is wired with —
the Vault, the sandbox provider, the scanners, and the drivers are
runtime-selected and trusted, even where a function takes one as an argument —
and it does not control code running inside the runtime's own process.

The invariants at stake:

- No agent writes to the Vault, the runtime's record store. Any level, any
  role.
- The runtime derives status; the model never reports it. A task's result has
  no status field.
- An agent may not be judged by an artifact it can write. Specs and acceptance
  tests are hashed before build. Here that also means the item's identity,
  label, and expected detector must never reach a workspace or sandbox the
  agent reads.
- Default deny: a capability not granted in policy is unavailable.
- Fail closed: a missing check, a missing capability, a harness error, an
  unreadable answer, or uncounted spend refuses or is reported as such. It is
  never counted as a pass or a catch, and never degrades silently.
- Every capability claim maps to an executable assertion that fails when the
  capability is deleted. Here: a control that stops catching an item must change
  the committed number, and CI must notice.

The mechanisms that matter most:

- Corpus pinning (`corpus.json` digests, `loadCorpus`) and what reaches a
  workspace or sandbox (`render`, the scripted seat's apply script).
- Classifying a run's outcome as caught, passed, or unreadable (`classify`,
  `recorded`, the critic arm's read of attempt 1, the strict verdict parser),
  and how rates and bounds are computed from those outcomes.
- The spending cap and metering in the model tier (`Spend`, admission before
  each call, cost from the usage records, refusal of an unmetered driver).
- The CI reproduction of the deterministic result and the gitleaks check over
  the corpus.
