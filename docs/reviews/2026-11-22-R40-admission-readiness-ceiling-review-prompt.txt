CONTEXT YOU NEED

The runtime admits "runs" (model-driven code changes against a git repository) at an autonomy level from L0 (manual) to L3 (autonomous). A separate readiness package scans one commit of the repository with probes (does it install from a lockfile, does it have tests, is the integration branch protected, and so on) and derives a ceiling from L0 to L2, naming the probe that holds it. This change makes admission (`admitRun` in packages/api/src/run.ts) scan the run's base commit through a port on the run request and refuse a run whose requested level exceeds that ceiling. It records the ceiling, or that no scan ran and why, in the admission record in the Vault (the runtime's append-only record store), and records the refusal in the enforcement record. The host's scanner (packages/api/src/readiness-scan.ts) caches reports, and the HTTP server hands it to every admission. Separately, a conformance assertion that each ceiling-bearing probe refuses over a fixture built to defeat it now requires the probe to report `absent` for the fixture's intended reason, not merely "not supported".

It must hold against a capable, motivated party trying to get a run admitted, or resumed, at a level above the readiness ceiling of the commit it runs on, or to have the record state a ceiling the scan did not derive. Assume no deceptive intent — only
that the easiest path gets taken.

That party controls the body of a run request sent to the HTTP API (workspace path, base commit, requested level, artifacts, approved cost), the contents and history of the target repository, and when the process stops. It does not control the components the runtime is wired with — the Vault, the sandbox provider, the drivers, and the readiness scanner the host builds are runtime-selected and trusted, even where a function takes one as an argument — and it does not control code running inside the runtime's own process. A library caller of `admitRun` may omit the readiness port; whether that is acceptable is part of the question.

The invariants at stake:

Default deny: a capability not granted in policy is not available. The readiness ceiling only subtracts: it may lower the effective level or leave it alone, never raise a level, grant a capability policy withheld, or admit a run policy refused. Its absence must be an explicit state, never an undefined value that disappears in a comparison and reads as clearance.

Fail closed: a missing required check, an absent capability, an unsupported stack, or a check that did not run is a refusal — never a silent downgrade, never a warning that lets the run continue.

The runtime derives status; the model never reports it. A recorded ceiling must be the runtime's derivation from probes that ran, not a value a caller supplied.

Every capability claim maps to an executable assertion that fails when the capability is deleted.

The mechanisms that matter most:

- `readinessAt` and the readiness branch of `admissionRefusal` in run.ts: where the scan is asked, which commit it is asked about, how its answer is checked, and how the refusal is derived from the record (including on resume).
- Where in `admission` the scan sits relative to the other refusals, the base snapshot, and the cost check, and what a thrown scan leaves behind.
- `ceilingAt` and `protectionStands` in readiness-scan.ts: the cache key, and when a cached report is trusted.
- `negativeFailure` and the NEGATIVE table in packages/conformance/src/registry/readiness.ts, and the new assertions in packages/conformance/src/registry/admission-readiness.ts.
