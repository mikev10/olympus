CONTEXT YOU NEED

A run is admitted at an autonomy level from L0 (manual) to L3 (autonomous). The level it may run at is the minimum of what was requested, two policy caps, and a ceiling derived by a readiness scan of the target repository. A scan can only lower the level, never raise it. This change makes admission refuse any run above L0 for which no scan ran — previously the missing scan left the level unchanged — records that refusal in the admission record, applies the same rule when a stopped run is resumed from its record, and reorders admission's checks so a missing control is reported before readiness. The test rigs, the benchmark, and the paid tests are given a scan port that answers a fixed ceiling. The range also carries one tooling change listing a paid test as intermittent.

It must hold against a capable, motivated party trying to get a run admitted, or resumed, above L0 without a readiness scan having bounded it. Assume no deceptive intent — only that the easiest path gets taken.

That party controls the run request (its requested level, its artifacts, its policy where the caller supplies one), the target repository's contents, and when the process stops and is resumed. It does not control the components the runtime is wired with — the Vault (the runtime's record store), the scan port when the host provides one, the sandbox provider, and the drivers are runtime-selected and trusted, even where a function takes one as an argument — and it does not control code running inside the runtime's own process.

The invariants at stake:

- Default deny. A capability not granted in policy is unavailable; a derived number may only subtract from the level, never grant one.
- Fail closed. A missing check, a missing capability, or an unsupported stack is a refusal — never a silent degrade, never a warning that lets the run continue. A caller that omits the scan is a missing check.
- The runtime derives status; the model never reports it. The admission record is the runtime's, and a resume reads the requested level and the readiness term from it, never from its caller.
- The runtime is a service; the CLI is a client.

The mechanisms that matter most:

- admissionRefusal and the readiness term it reads from the admission record, on admission and on resume, including records written before this change.
- The order of the controls and readiness checks.
- The scan ports given to test rigs, the benchmark, and paid tests, and whether any production path can reach one.
