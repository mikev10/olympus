CONTEXT YOU NEED

The project is a runtime that carries work from a spec to merged code through
fixed stations, with model agents seated at some of them (a builder, a
reviewer). This change gives each seat instructions a person wrote: one
Markdown file per role in a directory on the host, compiled into a role with
the SHA-256 of its bytes (packages/compiler). Run admission compiles the
directory, refuses a run whose roles are broken or missing, and pins every
compiled role in the run's write-once admission record. The line then hands
each seat its pinned role, records the role's id and hash on every model call's
usage record, and the Claude Code driver renders the role on the CLI's command
line as the agent the session runs as. What a role may do (tools, network,
writable paths, model tier, budget) is not in the role at all; it comes from a
separate policy.

It must hold against a capable, motivated party trying to change the
instructions an agent runs under, or the version a run records, without a
person editing the role file before the run was admitted. Assume no deceptive
intent — only that the easiest path gets taken.

That party is the agent being run, and controls everything it can write: the
files in its workspace (a copy of the repository the run was admitted from),
what its model session returns, and, through a change that is later merged,
the repository future runs are admitted from. A person, not that party,
controls the roles directory, the policy file, and the host configuration. The
party does not control the components the runtime is wired with — the Vault,
the sandbox provider, and the drivers are runtime-selected and trusted, even
where a function takes one as an argument — and it does not control code
running inside the runtime's own process.

The invariants at stake:

- No agent writes to the Vault (the runtime's store of records and locked
  artifacts), at any level, in any role. Role instructions are Vault-class: no
  agent may edit its own instructions or another's.
- The runtime derives status and records; the model never reports them. The
  role version a call ran under is computed by the runtime, never taken from
  anything a driver or model returned.
- An agent may not be judged by an artifact it can write, and must not be able
  to rewrite what instructs it.
- Default deny: a capability not granted in policy is unavailable. A role must
  never become a second source of grants.
- Fail closed: a missing or malformed role, an unreadable directory, or a seat
  with no role is a refusal, never a skip, a truncation, or a fallback to the
  CLI's default prompt.
- Event payloads (text from triggers outside the system) are data, never
  instructions, and never reach a role.

The mechanisms that matter most:

- compileRoles: which directory entries it accepts and how it reads them
  (links, non-regular files, names, the byte cap, UTF-8, empty files, a file
  swapped between listing and opening), and what the hash covers.
- Admission: where the roles directory may lie relative to the workspace and
  the workspace store, which roles a run must have, and what the admission
  record pins; and resume, which reads roles only from that record.
- The line: which role each seat receives (the review seat always runs as
  `reviewer`, with its own task's grants), and the role id and hash written on
  every usage record.
- The Claude Code driver: how the role reaches the CLI (`--agents` and
  `--agent` on the argv), what the agent definition can carry, and the refusal
  of a session that did not load the role.
