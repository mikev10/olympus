CONTEXT YOU NEED

The project runs a third-party agent CLI (Claude Code or Codex, installed from
npm) inside a Docker sandbox to do coding tasks, and keeps an evidence record
of every call so an auditor can tie a verdict to what produced it. This change
pins each CLI and its platform packages by sha512 in a lockfile committed
beside each driver's Dockerfile (`image/cli-lock.json`), installs from it with
`npm ci` followed by an install check (`image/check-install.js`), and has
`ensureImage` return the image's content ID, refusing a tag the Docker daemon
holds as an image this host has no record of building (records in
`~/.factory/images/`). The runtime provisions every agent call's sandbox from
that content ID and records it as `harnessImage` on the call's usage record and
on the evidence bundle that verifies the call's work. The Vault refuses a
record that names no content ID.

It must hold against a capable, motivated party trying to get an agent call
run in, or recorded as having run in, an image other than the one built from
the committed lockfile — through the npm registry serving other bytes for a
pinned version, a tag on the Docker daemon pointing at another image, or a
record that names an image the call did not run in. Assume no deceptive intent
— only that the easiest path gets taken.

That party controls what the npm registry serves for any package name and
version, which image a tag on the local Docker daemon points to between or
during runs, the files of the workspace a task writes, and everything an agent
CLI returns from inside the sandbox. It does not control the committed
repository (the Dockerfiles, the lockfiles, the install check, the runtime's
source), the host user's home directory where build records are kept, or the
components the runtime is wired with — the Vault, the sandbox provider, and the
drivers are runtime-selected and trusted, even where a function takes one as an
argument — and it does not control code running inside the runtime's own
process.
