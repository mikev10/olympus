CONTEXT YOU NEED

A runtime has AI agents change a target repository and then decides, from
evidence it collects itself, whether the work is done. These adapters are how
it understands a TypeScript repository tested with vitest or jest: which files
are test suites, what each test file asserts and whether a change weakened or
removed an assertion, which tests are skipped or focused, how much of the
changed code the tests executed, and which configuration files changed. They
read two directory trees — the repository before the change ("base") and after
it ("head") — on the runtime's own host, and they are meant to parse and never
execute anything in them. A separate adapter runs a command-line scenario
inside the sandbox container and compares what the process did against a
locked expectation, on the host. An adapter set records which of these
controls exist for a repository, and the most autonomous level of operation is
refused whenever any control is missing.

Two contract changes land with it: a check result now carries the runtime's
verdict on whether an expectation held, and the gate that decides pass or fail
reads that verdict instead of the process's exit code; and a sandbox command
can now be given standard input. The commit range also carries two small
changes that landed between reviews — a CI workflow change and a permissions
change in another package's test harness — which are in the bundle and in
scope.

These properties have to hold even when the repository under analysis is shaped
in the least convenient way the code allows. Assume no deceptive intent — only
that the easiest path gets taken, and that anything the code does not prevent
will eventually happen by accident.

What the code must treat as untrusted: every file in the base and head trees —
their contents, names, sizes, and types, including symbolic links, directories
where files are expected, and special files — and therefore every test file,
every framework config file, and the package.json. Also the contents of the
coverage report, which is written by a test run in which the repository's own
code executed. Also the process a command-line scenario runs: its output, its
exit code, what it does with its input, and anything it does inside the
container before or during the check.

What the code may treat as trusted: the paths the runtime passes in (the two
tree roots, the location of the coverage report, and the directory the
report's file paths are relative to); the scenario's input and expectation,
which come from acceptance criteria locked before the agent worked; the sandbox
provider, which is runtime-selected even where a function takes one as an
argument; and code running inside the runtime's own process. A finding that
depends on one of those being hostile is out of scope, because the trust
boundary sits outside them.

The invariants at stake:

I1 — No agent writes to the Vault, at any autonomy level, in any repository, in
any role, under any trigger. It is enforced at the mount layer, which only
holds for code that runs inside the container. For this unit it means nothing
from the repository under analysis may run on the host: a config that is
loaded, a tool that is spawned, or a module that is imported by a computed name
would run agent-written code outside the mount table.

I2 — The runtime derives status; the model never reports it. For this unit it
means a behavioral check's pass or fail is the runtime's own comparison, made
where the process under test cannot reach it, and a process's own exit code
never stands in for that verdict.

I3 — An agent may not be judged by an artifact it can write. The expectation a
scenario is compared against comes from locked acceptance criteria, never from
the implementation.

I5 — Fail closed. A missing required check, an absent capability, an
unsupported stack or configuration, an unreadable input, or a shrunken test
enumeration is a refusal — never a silent degrade, never a default that lets
the run continue, never a number reported for something that could not be
measured.

I8 — Every capability claim maps to an executable assertion that fails when the
capability is deleted. Documentation asserting that a subsystem is wired is not
evidence that it is.

The mechanisms that matter most:

- Test discovery: framework configs are read from their syntax tree, a binding
  is followed only when nothing else in the file refers to it, per-version
  discovery defaults are applied, and anything that cannot be resolved is
  refused rather than enumerated with defaults.
- Assertion comparison: how two lists of parsed assertions are paired, and the
  rule that decides which changes are reported as weakened, removed, or a
  widened tolerance.
- Reading agent-written trees on the host: link and special-file handling,
  size caps, the in-process line diff, and how the coverage report is parsed
  and its paths mapped onto the head tree.
- Judging a command-line scenario: validation of the scenario's shape, the
  command issued through the sandbox provider with its input, the comparison on
  the host, and the gate rule that a result carrying an expectation is judged
  by it rather than by its exit code.
