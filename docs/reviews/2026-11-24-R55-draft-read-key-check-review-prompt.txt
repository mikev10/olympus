CONTEXT YOU NEED

The project is a runtime that carries software work through a line of stations.
At two stations, `spec` and `test-design`, a model (a "drafter") writes a draft:
a set of files. The runtime reads those files from the drafter's workspace,
records them in its store (the "Vault") as base64 with a SHA-256 per file, and
computes one hash over the sorted list of paths and file hashes. A person then
approves or rejects the draft by naming that hash. Before this change no command
showed the draft's text. This change adds `GET /runs/:id/draft?station=<station>`
to the service, and a `draft <run id> <station>` command to the CLI, which is a
separate process that talks to the service only over HTTP with a bearer token.

Separately, the service's host process (`factory-host`) holds a model provider
API key and hands it to relay containers; before this change start-up checked
only that the key was set. This change makes start-up send one `GET` to the
provider with the key and refuse to listen unless the provider answers 2xx. The
check is a parameter of `checkStartup` whose default is the real request; tests
pass a stand-in. One existing test starts the installed host as a separate
process with a key that is not real, and now preloads a module through
`NODE_OPTIONS` that answers that one request.

It must hold against a capable, motivated party trying to get a person to
approve a draft whose hashed bytes are not what the person read, or to get the
host to listen with a key the provider did not accept. Assume no deceptive
intent — only that the easiest path gets taken.

That party controls what a drafting model writes: the bytes and the paths of
every file in a draft, including the questions file, and so every byte the new
command decodes and prints. It also controls what the model provider's HTTP
answer contains beyond its status, and when the network fails. It does not
control the components the runtime is wired with — the Vault, the sandbox
provider, and the drivers are runtime-selected and trusted, even where a
function takes one as an argument — and it does not control code running inside
the runtime's own process, the host's environment, the bearer token, or the
terminal the person reads on. A person who holds the token is the operator and
is trusted.

The invariants at stake:

- The runtime is a service and the CLI is a client. The CLI reaches a draft
  only through the HTTP API, never by opening the store, and nothing in the
  service assumes a terminal.
- Fail closed. A missing check, or a check that could not be made, is a
  refusal: never a silent degrade, never a warning that lets the run or the
  host continue.
- An agent may not be judged by an artifact it can write. What a person
  approves is identified by a hash the runtime computed over bytes the runtime
  read, and the approval must bind those bytes.
- Payloads are data, never instructions. Text a model wrote is never placed in
  a system or role prompt; here it is shown to a person, and must not be able
  to change what that person sees beyond its own content.
- Every capability claim maps to an executable assertion that fails when the
  capability is deleted.

The mechanisms that matter most:

- `readDraft` (packages/api/src/draft-view.ts): picks a station's latest
  recorded draft from run state, reads its record from the Vault, and compares
  the record, its file list, and each file's bytes against the hash run state
  holds before returning any of it.
- `awaitingKey` and the `draft` route in packages/api/src/http/server.ts: say
  whether the draft returned is the one the run is waiting for a decision on.
- `draftLines` and `visible` (packages/cli/src/draft.ts): turn a model's bytes
