CONTEXT YOU NEED

Before a model builds a change, a test-design stage writes and locks acceptance
tests and a verification manifest of checks; the runtime hashes them, and later
runs every check itself in a fresh sandbox with no network, over the base
commit plus the change, and derives the verdict from what it observed. This
unit adds a `property` check kind: a locked test file that states properties
with fast-check (`fc.assert(fc.property(...))`), run under the base's own
vitest, while a runtime-written preload, loaded through NODE_OPTIONS from a
read-only mount, sets the seed and the number of cases the manifest pins and
reports every run, located at the `assert` call that made it. The runtime then
compares those reports against the pin and against every registration it found
statically in the file, and that comparison is the check's verdict. It also
adds a policy field that can require a property check for each authorization
rule a spec names, and a benchmark corpus version with an item a property check
should catch and an arm that runs with property checks.

It must hold against a capable, motivated party trying to have a change judged
as passing its property checks when the properties do not hold for it, or
judged on fewer cases, another seed, or none. Assume no deceptive intent — only
that the easiest path gets taken.

That party controls the change: every file the build writes into the workspace,
its source and anything it adds, which then runs inside the check's process as
the code under test. It does not control the locked artifacts (the spec, the
manifest, the acceptance and property test files), which are hashed before the
build, nor the base commit or its dependency install, which the runtime makes
from the lockfile. It does not control the components the runtime is wired
with — the Vault, the sandbox provider, and the drivers are runtime-selected
and trusted, even where a function takes one as an argument — and it does not
control code running inside the runtime's own process.

The invariants at stake:

- The runtime derives status; the model never reports it. A verdict follows
  what the runtime observed, never a claim.
- An agent may not be judged by an artifact it can write. Specs and acceptance
  tests, property files among them, are hashed before the build and re-verified
  at every station transition.
- Fail closed. A missing required check, an absent capability, an unsupported
  stack, or a shrunken enumeration is a refusal — never a silent degrade, never
  a warning that lets the run continue.
- No agent writes to the Vault, and the Vault is never mounted into a sandbox.
- Every capability claim maps to an executable assertion that fails when the
  capability is deleted.
- Greek names never appear in code.
