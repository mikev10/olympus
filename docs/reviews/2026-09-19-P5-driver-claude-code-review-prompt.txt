CONTEXT YOU NEED

A runtime carries software work through a fixed line of stations, and a
"driver" is the component that actually runs a model on a task. This driver
runs the Claude Code CLI. The runtime provisions a container first — with a
mount table, an egress allowlist, and resource limits — and hands the driver a
handle to it. The driver is supposed to have no way to run anything except
inside that container, and to give the model a credential without that
credential landing anywhere the model or another process can read it.

Alongside the driver is a registry of executable assertions. Each capability
the driver declares about itself must map to an assertion that fails when the
capability is removed. Some of those assertions live in the driver package's
own test suite rather than in the registry; the registry counts one only after
reconciling it against a JSON report that the driver package's test run writes,
which is bound to the source tree by a content hash.

These properties have to hold even when the model behaves in the least
convenient way the code allows. Assume no deceptive intent — only that the
easiest path gets taken, and that anything the code does not prevent will
eventually happen by accident.

What the code must treat as untrusted: everything the model returns — every
token of narrative, every tool call it asks for — and the contents of the
workspace directory the container mounts as writable. Also the timing of
failures: a process killed mid-run, a container that dies, a test run
interrupted partway.

What the code may treat as trusted: the components the runtime is wired with.
The Vault, the sandbox provider and the drivers are runtime-selected, even
where a function takes one as an argument, as is code running inside the
runtime's own process. A finding that depends on one of those being hostile is
out of scope, because the trust boundary sits outside them.

The invariants at stake:

I1 — No agent writes to the Vault, at any autonomy level, in any repository, in
any role, under any trigger. This is enforced at the mount layer, not in
application code. For this unit it means the driver must run the model inside
the provisioned container and nowhere else: a driver that ran the CLI on the
host would be outside the mount table entirely.

I2 — The runtime derives status; the model never reports it. The task result
type has no status field. What the model says it did is a claim, stored
separately from evidence, and the two are diffed later.

I3 — An agent may not be judged by an artifact it can write. Specifications and
acceptance tests are hashed before the build stage and re-verified at every
station transition.

I4 — Default deny. A capability not granted in policy is not available. Adding
one is an explicit, versioned edit to a policy file.

I5 — Fail closed. A missing required check, an absent capability, an
unsupported input, or a shrunken test enumeration is a refusal — never a silent
degrade, never a warning that lets the run continue.

I6 — Reviewers never share the author's model family. The model family is an
explicit value a driver assigns; it is never inferred from a driver id, a
provider string, or a model name.

I8 — Every capability claim maps to an executable assertion that fails when the
capability is deleted. Documentation asserting that a subsystem is wired is not
evidence that it is.

The mechanisms that matter most:

- The driver holds a sandbox provider and issues every command through it;
  the credential travels to the CLI as an environment value on that call.
- The tool grant on a request is turned into CLI arguments that are supposed to
  decide which tools exist in the session, including for tools contributed by
  external MCP servers, which the driver inspects before running the task.
- The stream the CLI writes is parsed into events, usage counters, and a claim,
  with several conditions treated as refusals rather than as results.
- The reconciliation path: a run report written by one package's test suite,
  bound to the tree by a content hash, read by the registry to decide whether
  an assertion in another package counts.

THE QUESTION

Where does this code fail to enforce what it claims to enforce?

Two areas in particular. First: is there any path by which a tool, a network
destination, a filesystem path, or a credential reaches the model although the
request did not grant it — through an incomplete check, an ordering mistake, an
error path, or an argument that does not do what the code assumes it does?

Second: can the conformance registry report one of this driver's capabilities
as proven when the assertion behind it did not run, was skipped, failed, or ran
against different source than the tree being evaluated? An assertion that
reports success without exercising the property is worse than no assertion,
because it retires the pending entry that would otherwise have flagged the gap.

Report concretely:

1. Places where the mechanism can succeed while the property it protects is
   violated. Give the specific construction.
2. Checks that are tautological — that would pass regardless of the code under
   test.
3. Anything that fails open: an error, a missing file, an empty result, a
   skipped test, or a thrown exception yielding a pass.
4. Escape hatches specific to the language: casts, unknown, any, declaration
   merging, module augmentation, generic erasure, type predicates.
5. Ways the configuration can be satisfied without doing what it appears to do.
6. Which mechanisms you assess as sound, and why. If none are, say so.
7. Whether the framing above is right. If the adversarial question is the wrong
   question for this code, say so and explain what you would ask instead. That
   is a finding, not a digression.

HOW TO REVIEW
