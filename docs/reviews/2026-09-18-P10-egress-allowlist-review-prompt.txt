CONTEXT YOU NEED

This project runs AI coding agents inside disposable Docker containers. A
container is provisioned from a specification that names an image, a mount
table, resource limits, and an egress policy. The egress policy is either
`deny-all`, which has always been `--network none`, or `allowlist` with a list
of hosts, which until this change was refused outright because nothing could
enforce it. This change implements it: the container joins a Docker network
created `--internal`, and a filtering proxy container — started, owned, and
destroyed by the provider — sits on that network and on a second outbound
network, forwarding to allowlisted hosts and refusing everything else.

The bundle's commit range covers everything not yet externally reviewed. The
egress allowlist is the bulk of it; a smaller earlier change to the station
machine and the run line is also in range and is equally in scope.

It must hold against a capable, motivated party trying to reach a host the
allowlist does not name, or to make the conformance assertions report the
control as working while it does not. Assume no deceptive intent — only that
the easiest path gets taken.

That party controls everything running inside the provisioned sandbox
container: the processes it starts, the commands it runs, its environment
variables, its filesystem inside the container, and the contents of the mounted
workspace tree. It does not control the `SandboxSpec` handed to `provision()`,
the policy that produced it, the Docker daemon, the host, the provider's own
Node process, or the program the proxy container runs — those are
runtime-selected and trusted, even where a function takes one as an argument.
It does not control code running inside the runtime's own process.

The invariants at stake:

- Default deny. A capability not granted in policy is not available. Adding one
  is an explicit, versioned edit to a policy file.

- Fail closed. A missing required check, an absent capability, an unsupported
  configuration, or a control that cannot be enforced is a refusal — never a
  silent degrade, never a warning that lets the run continue.

- No agent writes to the project's Vault (its record of specs, evidence, and
  run state). Enforced at the mount layer: at most one read-write mount, and if
  there is one it is the workspace. No mount may be a Vault path, sit inside
  one, or contain one, at any mode.

- Every capability claim maps to an executable assertion that fails when the
  capability is deleted. Documentation asserting a subsystem is wired is not
  evidence that it is, and an assertion that would pass with the mechanism
  removed is not evidence either.

The mechanisms that matter most:

- The Docker network the sandbox container is placed on, created `--internal`,
  and what that leaves in the container's routing table.
- The proxy's host matching for both `CONNECT` and absolute-form HTTP requests,
  including how an authority string is split into host and port.
- The validation that runs before any container exists: which egress policies
  are refused, and which host strings are accepted into the proxy's list.
- The teardown path: what is removed, in what order, when a sandbox is
  destroyed, when its wall-clock budget expires, and when provisioning fails
  part-way.
