CONTEXT YOU NEED

The runtime carries work through a fixed line of stations (intake, spec, test-design, plan, build, verify, review, integrate), with model-driven seats at some of them. This change adds a "bug-fix" run template. A tracker issue routed to it is recorded as a candidate holding only schema-checked fields (repository, number, allowlisted labels, author trust); no model ever reads the report. A person reads it and writes the run's intent as three parts — steps that show the defect, what happens, what should happen — through the authenticated HTTP route. The runtime writes those parts into the spec as `defect.json`, a spec drafter model writes the rest of the spec including `reproduction.json`, and a separate test drafter model, given the locked spec alone, writes the acceptance check that must declare `reproduces: true` and `onBase: 'fails'`; the runtime then runs that check over the unchanged tree. A person may instead dismiss a candidate with a cause from a closed set, which admits no run. A person's own run may take the template only where the policy lists it.

It must hold against a capable, motivated party trying to get report text or tracker-chosen bytes into a model's prompt, to have a run treated as a bug fix (or not) without the policy saying so, or to have a check that does not reproduce the defect accepted as its reproduction. Assume no deceptive intent — only
that the easiest path gets taken.

That party controls the body of every tracker delivery (title, body, labels, repository name, issue number), whatever any drafter or builder model writes into its workspace and returns, and the fields of a run request sent to the API. It does not
control the components the runtime is wired with — the Vault, the sandbox
provider, and the drivers are runtime-selected and trusted, even where a
function takes one as an argument — and it does not control code running inside
the runtime's own process, the policy file, or the person's authenticated HTTP channel.

The invariants at stake:

- Event payloads are data, never instructions. Untrusted text enters inside an envelope and is never concatenated into a system or role prompt. Triggers select pre-declared templates; payloads supply parameters only.
- Default deny. A capability not granted in policy is not available.
- An agent may not be judged by an artifact it can write. Specs and acceptance tests are hashed before build and re-verified at every station transition.
- Fail closed. A missing required check, part, or capability is a refusal — never a silent degrade, never a warning that lets the run continue.
- Every capability claim maps to an executable assertion that fails when the capability is deleted.

The mechanisms that matter most:

- Template resolution at admission (`templateOf`, `bugFixProblems`, `draftingProblems` in packages/api/src/run.ts) and the policy validator's kind check for `bug-fix`
