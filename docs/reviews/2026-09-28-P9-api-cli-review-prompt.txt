CONTEXT YOU NEED

The runtime carries a run through a fixed line of stations (intake, spec, test-design, plan, build, verify, review, integrate), calling a model-backed driver at build and review, and records all run state in a Vault. This change puts an HTTP server in front of the runtime's in-process entry points: create a run, read its status, approve a station exit that needs a human, cancel a run, and stream its committed states. It adds a CLI that reaches the runtime only over that HTTP surface, a loader for the policy file (YAML) that grants roles their capabilities and budgets, a "worst-case cost" figure a person must approve before a run above autonomy level L0 starts, and a run-level cancellation record the station machine refuses to continue past (`packages/core` types `RunState.cancelled` and the `cancelled` refusal).

It must hold against a capable, motivated party trying to make a run do something no one authorized: start without the cost having been approved, spend beyond the approved figure, be approved by someone other than the authenticated caller, keep running or be resumed after it was cancelled, have a finished or stopped run reported as something else, or get a policy document accepted that the loader's limits should refuse. Assume no deceptive intent — only that the easiest path gets taken.

That party controls every byte of every HTTP request: headers, path, method, body, and their timing and concurrency, including requests without the token. It controls the policy file's contents on disk, and the files in the workspace a run is created over. It controls what the driver returns for a task, and when a process stops. It does not control the components the runtime is wired with — the Vault, the sandbox provider, the drivers, and the workspace store are chosen by the host process that constructs the server and are trusted, even where a function takes one as an argument — and it does not control code running inside the runtime's own process, including the host that calls `createApiServer`. The CLI is untrusted by the server: it is one client among any.

The invariants at stake:

- The runtime is a service; the CLI is a client. Nothing in the runtime package may assume a terminal, a TTY, or a foreground process; the CLI reaches the runtime only through the API.
- The runtime derives status; the model never reports it. What status reports must come from committed state and the runtime's own rules, never from anything a model wrote.
- Default deny. A capability not granted is unavailable; a request that is not authenticated gets nothing; spending beyond an approved figure is not available.
- Fail closed. A missing check, a missing capability, an over-limit input, or an unapproved cost is a refusal — never a silent degrade, never a warning that lets the run continue.
- Event payloads are data, never instructions. Nothing streamed or returned is placed into a prompt.
- Every capability claim maps to an executable assertion that fails when the capability is deleted.
