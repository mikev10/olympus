# Review automation — rulings made during execution

Every decision the executing session took on the maintainer's behalf while building
`tooling/review-automation`, in the order they were made, each with what it costs if it was
wrong. Extracted from the execution ledger, which is session scratch and is not kept. The
design decisions that shape the system are recorded more briefly in `D-TOOLING-01` in
`docs/decisions.md`; this file is the fuller trail behind them.

Read it for the ones to overturn. Several reverse or narrow something the maintainer chose at
the start, and several correct an earlier ruling of the controller's own.

---

1. Ruling: add `.superpowers/` to `.gitignore` — the SDD workspace holds this ledger and every review package, and an ungitignored scratch directory in a repo whose CI checks for stray tracked files is an accident waiting to be committed. `.gitignore` is a protected path under `.github/protected-paths.txt`, so this joins `package.json` and `vitest.tooling.config.ts` in the PR's declared-intent list. Costs if wrong: one line in a protected file the maintainer may prefer to keep out of the repo; trivially reverted.

2. Ruling: replace Task 2's tautological harness test with a real assertion — that the running Node major version is at least 22, which is the plan's own Global Constraint and a genuine precondition for the runner. The plan's text mandates a test that would pass regardless of whether the harness works, and this project's own review prompt calls tautological checks out by name (item 2, "checks that would pass regardless of the code under test"). Writing one into the first task would be indefensible. Costs if wrong: a marginally different first test; the harness is still proved to run by the file being collected at all.

3. Ruling: Task 8 must guard `main()` with a `process.argv[1]` comparison, not `import.meta.main`. `import.meta.main` landed in Node 24 and CI runs Node 22, where it is undefined — the guard would still be falsy and so test-safe, but the typecheck would need a lib bump to accept the property. Costs if wrong: a slightly wordier guard.

4. Ruling: Task 8's `parseArgs` must narrow the family with a type predicate rather than `family as Family`. The plan's Global Constraints forbid `any` and this project's review prompt flags casts as a language escape hatch; a guard is the same length as the cast. Costs if wrong: nothing.

5. Ruling: Task 1's global CLI install and the two interactive browser logins are done by the maintainer and the controller, not a subagent — a subagent cannot complete an OAuth flow in a browser, and the install is a side effect outside the worktree that the maintainer explicitly asked for ("we should install them"). The probe steps that follow authentication are dispatched normally. Costs if wrong: the controller spends a few turns on setup that a subagent could not have done anyway.

6. Task 1: step 1 done — installed via `npm install -g` (codex-cli 0.155.1, gemini 0.60.0). Ruling: used npm global rather than `pnpm add -g`, which failed with ERR_PNPM_GLOBAL_BIN_DIR_NOT_IN_PATH and wanted `pnpm setup` to rewrite the maintainer's shell profile. npm's global prefix is already on PATH. Installing two CLIs should not require editing a shell profile. Costs if wrong: the CLIs live under npm's prefix; uninstall is `npm rm -g` rather than `pnpm rm -g`.

7. Ruling: `codexArgv` drops `--ask-for-approval never` entirely — the flag does not exist in codex-cli 0.155.1 and the probe's first invocation died on it. The rollout log confirms `"approval_policy":"never"` is already the default for `exec`, so the behaviour the flag was meant to pin is what happens anyway. The plan's Task 7 test asserting `--ask-for-approval` must be replaced by one asserting the rollout log records approval_policy never. Costs if wrong: the argv no longer states that intent explicitly, so a future default change would be silent — mitigated by asserting on the recorded policy instead of the flag.

8. Ruling: `codexArgv` gains `--skip-git-repo-check`. The scratch work dir is not a git repo and codex refuses to run in one without it: "Not inside a trusted directory and --skip-git-repo-check was not specified." Without this the runner cannot start. Costs if wrong: none; the flag only waives a precondition that a throwaway directory can never satisfy.

9. Ruling: `modelFromEvents` cannot read the model from `--json` stdout for Codex — it is not there. stdout carries only thread.started / turn.started / item.completed / turn.completed. The model lives in the on-disk rollout log, event type `world_state`, field path `.payload.state.collaboration_mode.model` (measured: "gpt-6-astra"). Token usage likewise: `token_usage_record` → `.payload.usage`, which includes total_tokens that the stdout usage event omits. So the Codex path parses the rollout log, not stdout, and the plan's `modelFromEvents(family, jsonl)` takes the rollout log text for codex rather than stdout. Costs if wrong: a manifest with a null model, which is recorded honestly rather than guessed — but the evidence would be weaker.

10. Ruling: `CODEX_KEEP` becomes ['session_meta','turn_context','world_state', 'token_usage_record']. All four are confirmed present in the rollout log; `world_state` was absent from the plan and is the one carrying the model id. `event_msg` and `response_item` are excluded — they are the message bodies the stripping exists to drop. Costs if wrong: a slightly larger metadata log.

11. Ruling: the clean-room proof recorded in the manifest is the PRE-invocation listing, and the manifest additionally records a post-run file count. A single single-turn run left 332 files / 34MB in the scratch CODEX_HOME, mostly an auto-fetched default plugin and skill cache. That growth is the CLI's own vendor defaults, identical for every user and not the maintainer's context, so it is recorded rather than prevented — but `assertCleanRoom` asserting an exact allowlist can only ever run before the invocation, never after. Costs if wrong: vendor-default skills could carry instructions nobody audited; the post-run count makes the growth visible so a future session can investigate.

12. Ruling: Task 2 proceeds now, in parallel with the still-blocked Gemini probe. The plan gates all later tasks on Task 1 because Task 7 needs the isolation variable and the credential filenames. Task 2 consumes neither — it wires tsconfig, a vitest config, two root scripts, and two CI steps. Holding it idle while a human completes a browser login buys nothing. Costs if wrong: none; Task 2 touches no file any probe finding could change.

13. Ruling: Task 2's review range is e3c8f7a..f472bfb, not the recorded BASE ae0cc9f..HEAD. The controller committed three plan corrections to the same branch while the implementer was working, so the recorded BASE..HEAD span contains work that is not Task 2's. Reviewing that span would put the controller's own edits in front of a task reviewer as if the implementer wrote them. Costs if wrong: nothing for this task; the final whole-branch review covers every commit regardless.

14. Ruling: keep the `.ts` specifiers and add allowImportingTsExtensions to tsconfig.tooling.json only. Measured first: Node 24 native type stripping accepts `import './dep.ts'` and fails ERR_MODULE_NOT_FOUND on `import './dep.js'`. The runner is invoked as `node scripts/...ts`, so `.ts` specifiers are a runtime requirement, not a preference. packages/* use `.js` because they are compiled; scripts/ has no compiled sibling to point at, so the two conventions are correctly different. Switching scripts/ to `.js` would typecheck and then crash at runtime — the worst of the three options offered. Putting the flag in tsconfig.base.json would let every package import `.ts` and corrupt their emitted output, so the flag is scoped to tooling. Costs if wrong: scripts/ typechecks under a slightly different option set than packages/, which is already true (tooling adds `types`). If tsc objects to allowImportingTsExtensions alongside the base's `declaration: true`, the implementer adds `declaration: false` to the tooling config, still scoped.

15. Ruling: add a random 32-hex-character nonce as the last line of every bundle, `=== BUNDLE END === <nonce>`, and require the reviewer to echo it. Only content that exists solely at the tail can prove the tail arrived. Chosen over echoing the last N lines (brittle to whitespace and paraphrase) and over reporting a line count or section count (models count badly). verifyEcho collapses to two outcomes once a nonce exists: verified, or failed. `unverified` now means exactly one thing — the bundle carries no tail proof — which is the honest state for every bundle generated before this change, including P5's. Costs if wrong: a reviewer that mistranscribes 32 hex characters yields a false `failed`, which is the safe direction but will need a human to distinguish a transcription slip from real truncation. The runner's message must say so.

16. Ruling: the nonce proves the tail was DELIVERED, not that the middle was attended to. A model can receive the whole bundle and reason about only part of it, and no checksum detects that. The doc comments must not overclaim, and cross-family agreement plus the prompt's other items carry that load instead.

17. Ruling: restore 'unverified'. Both states refuse, so nothing unsafe would have shipped, but they are different facts and a human acts on the difference. `failed` means the check ran and was not satisfied — a reviewer problem, possibly truncation. `unverified` means no tail proof could exist, because the bundle predates the convention — an artifact-age problem with no reviewer implication. Collapsing them would also strand three already-specified downstream pieces: Task 5's outcomeOf branch and its INTEGRITY_UNVERIFIED outcome, Task 10's triage explanation of that state, and Task 12's smoke-test expectation. Costs if wrong: one extra union member carrying a distinction a future session might find unnecessary.

18. Ruling: re-order the remaining tasks to 9, 10, 11, then 7, 8, 12. Tasks 7, 8 and 12 need the Gemini probe, which is blocked on a browser login only the maintainer can complete. Tasks 9, 10 and 11 are skill and document changes that consume nothing from it: Task 9 owns review-request's prompt template, the bundle generator and the new run-review skill; Task 10 rewrites triage-review's input contract; Task 11 updates ship-unit, WORKFLOW.md and decisions.md. Stopping the whole run on a human login while three independent tasks sit ready would waste the wait. Costs if wrong: Task 9's run-review skill will reference `scripts/run-external-review.ts` before Task 8 creates it. That is harmless — nothing invokes the skill until Task 12, which is after Task 8 either way — but a reader browsing the branch mid-build would see a skill pointing at a script that does not exist yet.

19. Ruling (concern 1, Critical): the prompt's first paragraph said the bundle is "the attached file" and told the reviewer to stop if it is "not present in this conversation". In CLI mode there is no conversation and nothing is attached — Codex reads the bundle from its working directory, Gemini receives it injected. A reviewer following that literally would refuse on every run, and the refusal would read as diligence rather than as a bug. Reworded to be true in all three delivery modes. Note the controller's error here: the dispatch told the implementer the fixed sections must not change, and it over-applied that to a paragraph the skill treats as fill-in. The skill fixes the clean-room, calibration and output sections only. Costs if wrong: the prompt is one sentence longer and names three delivery modes where a chat-only reader needs one.

20. Ruling (concern 2): the implementer followed integrity.ts over the plan, and that was right. The code returns `unverified` only when the bundle carries no nonce; a reviewer that ignored the instruction now yields `failed`. The plan's Task 10 text still describes the older meaning and must be corrected before Task 10 is dispatched, or the triage skill will explain a state that cannot occur. Costs if wrong: nothing — the code is the authority and it shipped first.

21. Ruling (concern 3): the two generator assertions are prose a session is told to run, so a skipped one fails closed only after the bundle has been sent. Closing it structurally instead: Task 8's runner will refuse pre-flight when a bundle carries no nonce, before building a scratch directory or contacting any vendor, so an unverifiable bundle costs no egress. The shell assertions stay as the generator-side check. Costs if wrong: Task 12's smoke test can no longer run against P5's pre-nonce bundle, which forces a decision about what the first end-to-end run targets — recorded below rather than decided now.

22. Ruling (the two chat-mode phrases inside the fixed clean-room section): leave them unchanged, as the implementer recommended. They are "no conversation that produced it" and "from earlier conversations, stored memory". Both are negations or conditionals that stay true in a headless run and therefore cannot produce a false refusal, unlike "the attached file", which asserted a positive fact that was false. The skill fixes that section on the stated grounds that it is what separates a useful review from a list of style opinions, so changing it for no functional gain would spend that rule for nothing. The "stored memory" line is in fact MORE relevant now, not less: the real ~/.codex holds memories_1.sqlite and thread_history_1.sqlite, so the instruction is a second layer behind the scratch CODEX_HOME isolation. Costs if wrong: two phrases read slightly oddly to a reviewer that was never in a chat, with no behavioural effect.

23. Ruling (concern 2, the split case where one family counts and the other does not): triage may proceed on the counted review — a single counted review is what the manual loop produced for years and refusing outright would discard valid work. But the skill must recommend re-running the failed family first, because a re-run is one command and no human effort, and it must require `Cross-family agreement:` to record the split explicitly. The property being protected: a unit reviewed by one family has one independent pass, not two, and nothing may later read as though both ran. Rotation was retired precisely because both families now review every unit; a split run triaged as normal would claim scrutiny the unit did not get, in the record this project's central claim rests on. Costs if wrong: one more field the maintainer must fill honestly, and a recommendation they may routinely decline.

24. Ruling (concern 1): accepted as resolved by the implementer, and its judgment was better than the brief's. "A run whose outcome is not `counted` is not a review" is true of a single run; compressed to "triage does not begin" it contradicts shipped triage-review, which says a single counted review IS a real review and is not refused. Those are different claims about different things. The implementer kept both rather than picking one. The brief was loose, the code was specific, the code won.

25. Ruling (concern 2): accepted. Three scope widenings, all inside files already in scope, all forced by a verification the controller mandated — a check demanding zero hits for four chat-era phrases necessarily reaches every line carrying one. The REVIEW READY banner and clipboard step in WORKFLOW-DIAGRAM.md were already gone from the shipped skill, making them stale documentation of a step that no longer exists, which is the defect this task existed to fix.

26. Ruling (concern 3): authorized the implementer to edit the existing preamble line in docs/decisions.md. The append-only constraint existed to stop an implementer rewriting prior decision entries, not to freeze the file's description of itself. The preamble says the log records "calls made while executing a unit", and D-TOOLING-01 was not; a file that mis-describes its own contents by one section invites a future reader to conclude the section does not belong and remove it. Costs if wrong: one clause added to a preamble, trivially revertible.

27. Ruling: D-TOOLING-01 and the new section heading accepted. The implementer rejected D-REVIEW-* because eight existing sections are already named "external adversarial review", so a bare D-REVIEW-03 would read as a unit's. Sound.

28. Ruling: Gemini authenticates by a PAID GEMINI_API_KEY. Verified against Google's API terms before recommending: the free tier says Google uses submitted content "to provide, improve, and develop Google products and services" and that "human reviewers may read, annotate, and process your API input and output"; the paid tier carries no such use and the DPA applies. The bundle is the full source of every changed file, sent on every unit, so the free tier was disqualifying on privacy rather than on cost. Measured cost at ~100k input tokens: about $0.20 per review against Gemini 3.1 Pro, $0.125 against 2.5 Pro, $0.075 against 3.x Flash — negligible at one unit per session, which retires the metering concern that drove the original choice. Gemini 3.1 Pro has no free tier at all, so free would also have meant a weaker adversary. Costs if wrong: a few dollars a year, and a key the maintainer must keep valid. Alternatives rejected: Vertex AI (same guarantee, heavier setup, worse isolation story than one env var) and dropping to Codex alone (loses the cross-family signal that justified retiring rotation, and leaves one vendor as a single point of failure).

29. Ruling: a secret never enters a committed artifact. The manifest is committed and records envOverrides, so it records variable NAMES and redacts any value whose name matches /(_KEY|_TOKEN|_SECRET|PASSWORD)$/i. The same rule binds stderr capture, the stripped session log, and every error message — a refusal that prints the environment is a refusal that commits the key. Added to Global Constraints with a verification step. Costs if wrong: the manifest records one less fact about the run, which is the correct trade.

30. Ruling: the Gemini model is pinned to gemini-3.1-pro-preview, departing from the design's "never pin" principle, because an API call must name a model where a CLI can choose its own default. The reported modelVersion is recorded separately, so the manifest still derives what actually ran. There is NO automatic fallback to another model: a -preview model can be retired, and when it is the call must fail loudly (HTTP 404) rather than quietly downgrade the adversary. The probe script used a fallback loop for convenience; production code must not. Costs if wrong: a retired preview model stops every Gemini review until the constant is updated — deliberately loud.

31. Ruling: ingestion floor = payload bytes / 5. Measured 3.18 and 3.20 bytes per token, so honest runs clear it by a wide margin; both measured failures (32,893 tokens when Gemini navigated; 24,181 when Codex could not read) fall far below the floor of 80,732 for the P5 bundle. Checked BEFORE the echo verdict in outcomeOf because it is the harder fact — measured by the vendor rather than reported by the model. An ingestion failure maps to INTEGRITY_FAILED, so the four-member Outcome union that Tasks 10 and 12 are written against is unchanged; the manifest's `ingestion` field records which cause applied. Costs if wrong: a tokenizer more efficient than 5 bytes per token on code would false-fail honest runs — none observed, and the floor is a named constant.

32. Ruling: the delimiters around the inlined bundle are <<<BEGIN REVIEW BUNDLE>>> and <<<END REVIEW BUNDLE>>>, and a test asserts they match neither the section header pattern ===== path ===== nor the nonce line. A delimiter shaped like either would be reported back as "the last section" or "the last line" and fail every run's echo check. The probe's <<<BUNDLE delimiters worked by luck; the plan makes it deliberate.

33. Ruling: the manifest's argv/envOverrides become a discriminated `invocation` (cli | api). The api variant records header NAMES only, never values, and its URL carries no key because the key travels in the x-goog-api-key header. cleanRoom and postRunFileCount become nullable, with null documented as "this transport loads no local configuration", which is a different fact from an empty listing. Task 5's shipped types are revised by Task 7; that is legitimate because Task 7 is reviewed like any other.

34. Ruling: Task 8 greps the manifest it just wrote for the first 8 characters of every secret-named environment value and, on a hit, deletes all three output files and exits non-zero. The Global Constraint's verification step is made structural rather than left to a reader.

35. Ruling: enforce it in the type instead, using this repository's own branded-type idiom (`string & { readonly __brand: 'X' }`, as RunId, SandboxHandle and ModelFamily already are). RedactedEnv and KeylessUrl, each with a single construction site carrying a comment, and two @ts-expect-error tests so that typecheck fails if either brand ever stops working — the same proof the conformance suite uses for its own brands. Costs if wrong: two casts, each confined to one commented function.

36. Ruling: redactEnv is DEFAULT-DENY, replacing the Global Constraints' name-pattern blocklist /(_KEY|_TOKEN|_SECRET|PASSWORD)$/i. Values are recorded only for CODEX_HOME, HOME and USERPROFILE; everything else becomes "<redacted>". A blocklist cannot anticipate every secret — DATABASE_URL carries a password and matches no suffix — and this project's own invariant is that a capability not explicitly granted is unavailable. Costs if wrong: a future legitimate override reads "<redacted>" in the manifest until someone adds it to RECORDABLE_ENV, which is the correct failure direction.

37. Ruling: keylessUrl REFUSES a URL with any query string or userinfo rather than stripping it, and its error message deliberately omits the URL, because an error that echoes a key-bearing URL commits the key.

38. Ruling: runCli launches process.execPath with Codex's JS entry point. The entry point is resolved without spawning npm (itself a .cmd): CODEX_JS env override first, then %APPDATA%\npm\node_modules\... on Windows, then <execPath>/../lib/node_modules/... on POSIX. If it does not exist the runner refuses, naming what it looked for; there is no fallback to a shell. Costs if wrong: a non-standard npm prefix needs CODEX_JS set, and the refusal says so.

39. Ruling: async spawn with streamed output, never spawnSync with `input` — the latter's default maxBuffer would silently truncate a long --json event stream.

40. Ruling: tests never invoke the real Codex CLI or the network. runCli is tested by spawning process.execPath with an inline script that echoes stdin (proving stdin is written AND ended) and one that sleeps forever (proving the timeout kills).

41. Ruling: remove the unmeasured top-level fallback. In a check that GATES a run, a fallback path widens what gets accepted. If a future Codex moves the field, the runner must return null and refuse, not read a location nobody verified — refusal is the failure direction this project chooses. Codex parsers should also key on the specific measured record type rather than any record carrying the field. Costs if wrong: a Codex upgrade that relocates the field stops every Codex review until the path is re-measured, loudly. Task 7B: under review, with the fallback removal named as a check.

42. Ruling (Task 7C, added beyond the plan): the Gemini request sets generationConfig.maxOutputTokens generously. Gemini applies a default output limit, and a long review that reaches it returns truncated with finishReason MAX_TOKENS. The plan already treats any finishReason other than STOP as a failure, so a truncated review would refuse rather than pass — the fix is not for safety but to stop honest long reviews being refused. Costs if wrong: a higher ceiling on output-token spend per review, bounded and small.

43. Ruling: record serviceTier in the manifest verbatim, and do NOT describe it as evidence of paid billing. Costs if wrong: none — it is recorded, not interpreted.

44. Ruling (Task 8, added beyond the plan): the post-write secret check and the manifest assembly become separately exported, unit-tested functions rather than inline steps in main(). The secret check is the last line of defence for a committed artifact and is pure over file contents and an env map, so it should be tested without the network; it returns secret NAMES, never values. Costs if wrong: two more small exports.

45. Ruling (Task 8): the api transport has no process exit code, so the runner derives one — 0 when the call succeeded AND the reply is complete, non-zero otherwise — and timedOut from an abort. That lets outcomeOf stay unchanged and maps an incomplete Gemini reply (finishReason not STOP, or thought-only) to FAILED rather than to a counted review.

46. Ruling (Q1): GeminiResult gains nullable `responseId` and `usageMetadata`, populated by parseGeminiResponse. Task 8's implementer is authorized to change gemini.ts and its test for this ONLY. Rejected the alternative of the runner wrapping fetchImpl to capture the raw body: that would put the runner in contact with a function receiving the key header and parse the response twice. Returning the fields from the parser keeps the key inside gemini.ts. With the raw usageMetadata in the session line, serviceTier is recorded verbatim, satisfying the earlier ruling, and is interpreted nowhere. Costs if wrong: two nullable fields on a type.

47. Ruling (Q2): Manifest.cliVersion — for codex, read `version` from the package.json beside the resolved entry point, refusing if absent rather than recording a placeholder; for gemini, record 'api:generativelanguage/v1beta', a self-describing value, because the field is named cliVersion and the api transport has no CLI. The field is not renamed. Costs if wrong: a field name that fits one of its two transports imperfectly.

48. Ruling (Q3): the governing principle is that A RUN THAT CAUSED EGRESS LEAVES EVIDENCE THAT IT DID. Refusals before egress write nothing. Runs after egress that do not count always write .run.json and .session.jsonl, and write the .md only when a reply exists — including on integrity failure, since what the reviewer said is diagnostic and triage refuses it by outcome. AMENDMENT to the implementer's proposal: an approval policy other than "never" does NOT write nothing — Codex ran, so the bundle left the machine, and hiding that would be dishonest. Instead a synthetic non-zero exitCode goes into outcomeOf, which derives FAILED; the same mechanism the api transport already uses, so the outcome stays derived rather than declared. Costs if wrong: failed runs leave files in docs/reviews/ that a maintainer must recognise as uncounted — which the manifest's outcome field states.

49. Ruling (Q4): P5's artifacts live only on unit/p5, so a P5 dry-run here refuses at step 1 and never reaches the nonce check. P10's prompt and bundle are tracked on this branch and predate the nonce, so P10 dry-runs demonstrate the step-4 pre-flight refusal. Run both. The step-1 message must name the unit and say no committed review prompt was found, so a maintainer on the wrong branch can tell.

50. Ruling (concern 2, treated as the more serious): the Codex child's environment is exactly { CODEX_HOME }. Previously it inherited every parent secret, including GEMINI_API_KEY, and Codex has a read-only shell — a reviewer running printenv could put the Gemini key into its review, which is committed. The bundle is input Codex reads, and the project's invariant that payloads are data not instructions exists because text in a payload can try to behave like one. One variable makes every parent secret unreachable from inside the reviewer. Costs if wrong: on a platform where Codex needs more, it fails to start and the run records FAILED — loudly.

51. Ruling (concern 1): findLeakedSecrets targets an explicit secret set, not every non-recordable variable. Redaction and detection are different questions with opposite shapes: redaction answers "what may be written" and a miss WRITES a secret, so it stays default-deny; detection answers "did a known secret appear" and a false positive DESTROYS genuine evidence after the bundle was already sent, so it must be precise. The implementer measured the false positive on Windows — any reply quoting a C:\Users\ path tripped APPDATA and TEMP and rolled back a valid review. The secret set: GEMINI_API_KEY and OPENAI_API_KEY values; values of variables named /(KEY|TOKEN|SECRET|PASSWORD|CREDENTIAL)/i; and every string of 16+ characters in the copied auth.json, which holds the maintainer's ChatGPT OAuth tokens and which the runner handles. Safe to narrow because, with the Codex child holding only CODEX_HOME and Gemini's model seeing no environment, no env value can reach a reply through a reviewer; the check is now a tripwire for the runner's own bugs, and GEMINI_API_KEY acts as a canary for any bug that dumps process.env wholesale. Costs if wrong: a secret in an oddly-named variable that our own code wrote by mistake would not be caught — but no code path writes environment values except through redactEnv.

52. Ruling (added to fix round 1): distinguish, rather than remove, the refusal. An existing counted .run.json still refuses — a real review must never be overwritten or superseded. Any other existing outputs for the unit and family are ARCHIVED by inserting `.attempt-<N>` before the extension (lowest free N) and the run proceeds. Archive rather than overwrite or delete because a failed run's files are the record that the bundle was sent; the earlier principle applies — a run that caused egress leaves evidence that it did. The fixed filenames keep pointing at the latest attempt, so the shipped skills still find it, and the archived names cannot match the patterns the skills search for. Archiving happens after every pre-egress refusal, so a doomed rerun archives nothing; dry-run archives nothing and reports what it would. Costs if wrong: docs/reviews/ accumulates .attempt-N files for units with failed runs — each of which is a true record of an egress.

53. Ruling: option B. Search only string values under `tokens` (recursively) and a top-level string OPENAI_API_KEY. Rejected option A (every string minus timestamp-shaped ones) because it is the "everything minus exceptions" shape the controller had just rejected for environment variables, and it breaks the next time Codex adds a non-secret field that collides. Detection targets credentials precisely. Costs if wrong: a credential stored outside `tokens` in a future Codex format would not be searched — but no code path writes auth.json content.

54. Ruling: re-read the scratch auth.json AFTER the run and before removeScratch, and add its credentials to the secret set. Closes the implementer's stated limit that tokens refreshed mid-run were not searched.

55. Ruling: if Codex refreshed its credential during the run, write the scratch auth.json back to ~/.codex/auth.json atomically (sibling temp file, then rename), print one line saying so and nothing of the value, and do so regardless of the run's outcome. Reason: refreshed tokens exist only in the scratch copy, which is then deleted; if OpenAI rotates refresh tokens, every review that triggers a refresh would leave the maintainer's real credential dead, breaking their interactive Codex login and the next review's copy. NOT MEASURED whether OpenAI rotates — but the write-back is correct either way, since it writes valid newer tokens over older ones, which is exactly what Codex does in normal use. This is a write OUTSIDE the worktree to the maintainer's real config; it only ever writes what Codex itself wrote, and only when content changed. Costs if wrong: a race with the other product sharing ~/.codex if both refresh at once — mitigated by the atomic rename; and one more file the runner touches that the maintainer should know about.

INCIDENT, 2026-09-21, controller error. While measuring whether child.kill() orphans Codex's native process on Windows, the controller's script listed every process matching /codex/i and then ran a cleanup loop doing `taskkill /T /F` on every match. Four Codex processes belonging to the MAINTAINER'S OWN running Codex desktop app existed before the test (codex.exe 56188, codex-computer-use-swift 37004, codex-code-mode-host 59328, sandbox service 41824). The script misclassified them as orphans and force-killed 56188 and 37004 and their tree. The sandbox service survived (session-0 service; the kill failed). The app restarted under new PIDs (codex.exe 68072, computer-use-swift 67952). Its SQLite databases reopened with fresh WAL files at 15:18 and show no sign of corruption; WAL mode is designed to survive an abrupt stop. Whether an in-app task was in progress cannot be seen from outside. The maintainer was told immediately and plainly. Lesson, binding for the rest of this run and for the runner: NEVER select processes to kill by name pattern. Kill only PIDs this code itself spawned. The runner already complies — runCli only ever calls kill() on its own child.
