# Decisions: R60

## A-R60-01: what R60 builds, and the contract changes it opens with

Confirmed by the maintainer on 2026-11-28, in R60's session, each of six
questions taking the recommended answer. `/start-unit R60` stopped before any
code: the entry needed contract changes it did not declare, one deliverable
contradicted a standing registry entry, and it had no out-of-scope list and no
done-when. Read on `v2` at 47e13f3. Three points below go past what was asked
and are marked **new**; merging this confirms them with the rest.

### What the code holds against the entry as it was

- **A drafted manifest carries judgments, not only facts.** Beside `id`,
  `kind`, `required`, `timeoutMs` and `tests`, a check declares `onBase`,
  and may carry `deniesRule`, `reproduces`, a property check's `seed` and
  `numRuns`, and a behavioral check's `command`
  (`packages/integrity/src/types.ts:29-156`). Two are required of a draft: a
  spec naming an authorization rule is sent back without a check that names
  it (`packages/api/src/drafting.ts:693`), and a bug fix without a check
  that reproduces the defect (`drafting.ts:696`). No code can read any of
  these off a test file.
- **Policy holds no timeout.** `packages/core/src/policy/types.ts` has no
  such field. The only timeouts written by code are the constants `init`
  puts in the verification manifest (`packages/api/src/init.ts:129`).
- **`init` records no stack facts.** It detects a stack string
  (`init.ts:181-186`) and writes a policy, an environment file, a
  verification manifest, a graph, roles and rubrics (`init.ts:232-246`).
  None holds a framework or a test directory. Nothing in `packages/*/src`
  derives a test directory; `testDirectory` appears in `spec-parts.ts` and
  `drafting.ts` alone. A run admitted through the API has no `init` at all.
- **The base is judged on an exit code.** `CheckResult` is `exitCode`,
  `stdout`, `stderr`, `suiteCount` and two fields for other kinds
  (`integrity/src/types.ts:222`). `baseMismatches` reads a declared check as
  failed when its exit code is not 0 (`packages/api/src/base.ts:46`). A test
  whose import does not resolve and a test whose assertion fails are the
  same record.
- **The entry's retry code contradicts a registry entry.**
  `I3.base-refusal-tells-the-drafter-nothing-of-the-repository`
  (`packages/conformance/src/registry/drafting.ts:729`) holds the test
  drafter's retry to one fact: its draft did not hold over the repository.
  `RetryPart`'s `base-refusal` carries nothing
  (`packages/core/src/station/types.ts:163-171`). The test drafter is kept
  from the repository so that its tests judge the spec and not an
  implementation it has seen. Whether an import resolves is a fact about
  the repository, so a code for it would let a drafter ask which files
  exist, one answer per retry.

### What was decided

1. **The test drafter writes test files and one declarations file.** The
   file sits where the manifest did, under the run's drafts directory. It
   lists each test file with `onBase`, and where they apply `deniesRule`,
   `reproduces`, and that the file is a property test. The runtime builds
   `acceptance.json` from it: one required check per test, an id derived
   from the test's path, the kind, `tests`, the timeout and case count from
   policy, and a property check's seed derived from the test file's bytes.
   The built manifest is one of the draft's recorded files, so the draft's
   hash covers it, the critic reads it, and the lock writes it; no record
   type changes. An `acceptance.json` the drafter writes is a stray path,
   discarded unread.
   - **New:** a behavioral test's `command` stays the drafter's, written in
     the declarations file. It says how the product is run, which is a
     judgment, and dropping it would end drafted behavioral checks. A
     declaration with a command is a behavioral check; one marked as a
     property test is a property check; any other is an acceptance check.
   - Rejected: every test file a required acceptance check that fails on
     the base, as issue #195 proposed. A bug fix, a spec with an
     authorization rule, a property check and a test that guards existing
     behavior could no longer be drafted.
2. **Policy gains what the runtime writes into a drafted check.**
   `draftedChecks: { timeoutMs, propertyRuns }` in
   `packages/core/src/policy/types.ts`. A run admitted to draft its tests
   under a policy without it is refused at admission, naming the field. The
   policy `init` writes carries it. A policy written before this refuses a
   run that drafts tests until a person adds the field.
   - Rejected: a constant in the runtime. Nobody could set it, and a slow
     suite would have no recourse but a supplied manifest.
3. **The runtime derives the stack facts from the base at `spec`.** The
   framework and the test command come from the adapter detector `init`
   and `verify` already use. The test directory is the deepest directory
   holding every suite the base's runner enumerates. The runtime composes
   the run-requirements part from these and the drafter's
   `publicInterface`, and the composed file is what the draft records and
   the lock covers. `RunRequirements` keeps its four fields.
   - **New:** where the base's runner enumerates no suite, or the directory
     derived is the tree's root, code has nothing to derive. The spec
     drafter is told so and writes the test directory, as it does today,
     held to the same rule (`isDraftableDirectory`, `spec-parts.ts:55`).
     Rejected: refusing to draft tests on such a base, which would refuse
     every repository that has no test yet.
   - Rejected: reading the facts from a record `init` leaves. There is no
     such record, and one in the repository would be a file an agent can
     write.
4. **A test that did not load is not a failure on the base.** The runtime
   runs an acceptance check with the runner's machine-readable report and
   the adapter reads each named test's outcome from it. `CheckResult`
   gains `tests: ReadonlyArray<{ path, outcome: 'passed' |
   'assertion-failed' | 'did-not-load' }> | null`. `BaseMismatch.cause`
   and `BaseRefusalPart.cause` gain `did-not-load`. An acceptance check
   declared to fail is a mismatch unless every test it names is
   `assertion-failed`. A report the runtime cannot read is never read as an
   assertion failure.
   - **New:** the rule is `baseMismatches`' own, so it holds for a manifest
     a run was admitted with as it does for a drafted one. Exempting a
     supplied manifest would leave the gap open on the path a person uses.
     Both shipped stacks get it, or the one without it is refused.
   - Rejected: matching text in the check's output. The drafted test
     writes that output and can print anything.
5. **The retry is told nothing new.** A draft sent back for `did-not-load`
   goes back as `base-refusal`, bare. The cause is in the decision record
   and in `status`, for a person. In issue #210 the wrong import path came
   from the spec, so a code would not have let the test drafter correct it.
   - Rejected: a `did-not-load` retry code with no path. It weakens the
     registry entry above and needs a `RetryPart` change.
6. **R60 opens with this amendment,** and its entry gains the out-of-scope
   list and the done-when it lacked (`docs/plan/DECOMPOSITION.md`).

Gate paths R60 will touch: `packages/integrity/src/types.ts`,
`packages/core/src/station/types.ts`, `packages/core/src/policy/types.ts`,
`packages/conformance/`. The test drafter's and the spec drafter's role
files change, so their hashes do.

**Reverse** by restoring the entry. The manifest and the stack facts are
then a model's again, and a test that cannot load passes the base run.
