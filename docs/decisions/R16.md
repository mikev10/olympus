# Decisions: R16

## Amendment: bug-fix intake (R16)

R16 was started on `v2` at 5465731 and stopped before any code. Its
dependencies have shipped (R15, R19, P14, R22, each tagged `reviewed/*`), and
the two I7 controls it waits on are registered
(`packages/conformance/src/registry/triggers.ts:216`, `:261`). But its entry
names no contract amendments, no gate paths, and no way to declare a run a bug
fix, and what it binds needs five contract changes. So this is an amendment,
confirmed before it is built. The maintainer chose all six open questions on
2026-11-09, each the recommended answer.

### D-A-BG-01: what R16 found on `v2`

- **No bug-fix template.** The registry is `intake-candidate`,
  `observe-signal`, and the job templates
  (`packages/core/src/trigger/schemas.ts:35`). The `issue` kind and its schema
  exist: repository, number, allowlisted labels, author trust, and no free
  text (`schemas.ts:155-160`).
- **A person's run names no template.** The default policy gives `human` an
  empty template and enters it at `intake`
  (`packages/core/src/policy/default.ts:55-60`, D-P3-05). Nothing a person
  sends says what kind of work a run is.
- **An intent is free text.** `Intent` is `{ text, from: 'principal' }`
  (`packages/api/src/run.ts:169`), checked only for shape and a 32 KiB cap
  (`run.ts:543-554`). It has no parts to require.
- **The spec has three parts beside `spec.md`.** `SpecPart` is `security`,
  `run-requirements`, and `questions`
  (`packages/core/src/station/types.ts:192`). None holds where a defect shows
  or what a check needs to run it.
- **Every run already needs a check failing on the base.** Validation refuses
  a manifest with no required acceptance or behavioral check declaring
  `onBase: 'fails'` (`packages/api/src/validate.ts:267`, D-A-BF-01), so R16's
  `test-design` rule adds only what ties that check to the defect.
- **A candidate is admitted or expires, and nothing else.** `IntakeEntry`
  carries `admittedAs` and `expiredAt` (`packages/vault/src/types.ts:752-761`);
  the Vault has `markCandidateAdmitted` and `markCandidateExpired`. A person
  cannot record that a report was not worked.
- **R10 named a source for R16.** `InputSource` includes `'trigger-fields'`
  (`packages/core/src/run/types.ts:269`), and `narrowRun` narrows a run
  whenever it is called (`packages/api/src/line.ts:905`). Its only caller today
  is R10's conformance (`packages/conformance/src/registry/ratchet.ts:414`).

### D-A-BG-02: `bug-fix` is a registered template, and policy names the templates a person's run may take

- **Chosen (A-R16-01):** `TemplateId` gains `'bug-fix'`, valid on `issue`
  alone. A `bug-fix` delivery records a candidate exactly as `intake-candidate`
  does; nothing runs. `TriggerPolicy` gains `runTemplates`, the templates a
  person's own run may name, empty by default. `RunRequest` gains `template`
  (A-R16-02). A run admitted from a `bug-fix` candidate is a bug-fix run, and a
  request naming another template is refused. A person's run naming a template
  `runTemplates` does not list is refused. The admission record holds the
  template.
- **Rejected:** *`taskTemplate.human: 'bug-fix'`.* Every human run would be a
  bug fix. *A template inferred from the intent's shape.* A shape the caller
  chose would select the route, where policy must (I4).
- **Must hold:** I4, because no run is a bug fix unless a person's policy lists
  the template or its trigger's template is `bug-fix`. A run with no template
  admits exactly as before.
- **Reverse:** drop `runTemplates`, so a bug fix enters only through an `issue`
  candidate.

### D-A-BG-03: a bug-fix intent is three required parts, and the run drafts both artifacts

- **Chosen (A-R16-02):** `Intent` becomes a union. The R19 arm is unchanged.
  The bug-fix arm is `{ from: 'principal', template: 'bug-fix', steps, actual,
  expected }`, each a non-empty string, under the existing cap on their sum.
  Admission refuses one missing a part, naming the part, and refuses a bug-fix
  run whose spec or acceptance tests are supplied rather than drafted, naming
  the artifact. The intent record holds the parts as given.
- **Rejected:** *a supplied spec.* The entry gives the spec to R19's drafter
  and the check to R19's test drafter, which sees the locked spec only. A
  supplied test would be written by someone who read the report, which is the
  path D-A-BF-02 closed. *Parts as headings inside free text.* A heading can be
  forged or omitted, so the check would be a parse, not a type.
- **Reverse:** allow a supplied spec, checked for the same parts.

### D-A-BG-04: the spec gains `defect`, written by the runtime, and `reproduction`, written by the drafter

- **Chosen (A-R16-03):** `SpecPart` gains `'defect'` and `'reproduction'`. The
  runtime writes `.drafts/<run id>/defect.json` from the intent record's three
  parts before the spec drafter runs. The drafter writes
  `.drafts/<run id>/reproduction.json`: `{ where, needs: { data, accounts,
  services } }`, `where` a non-empty string and each `needs` entry a list,
  empty meaning none. Both lock with the spec. In a bug-fix run either part
  missing or failing to parse is refused at `spec`, naming it, and a `defect`
  part whose bytes are not the runtime's is refused there too. The security
  part (R17) stays required.
- **Why the runtime writes `defect`:** the test drafter is granted the locked
  spec only, so the steps it follows must be in the spec. A drafter copying
  them could reword them, and the check would follow the drafter's account,
  not the person's.
- **Rejected:** *steps, actual, and expected inside `reproduction`, written by
  the drafter.* It is the rewording above.
- **Reverse:** one `reproduction` part written by the drafter, compared against
  the intent by the critic.

### D-A-BG-05: a check declares that it reproduces the defect, and the runtime checks the declaration

- **Chosen (A-R16-04):** `AcceptanceCheckSpec` gains optional
  `reproduces: true`, which must sit with `onBase: 'fails'`. A bug-fix
  manifest with no required check declaring it is refused at the `test-design`
  exit, named. A non-bug-fix manifest declaring it is refused as not
  applicable. R15's base run proves that the check fails. Whether it follows
  the spec's steps is a line added to the shipped `test-design` rubric, which
  the critic judges.
- **Known limit:** no code can tell that a check follows prose steps. A check
  that fails on the base for an unrelated reason passes the runtime and rests
  on the critic, and with one driver on a person. That is D-A-BF-01's limit,
  and mutation testing (M3) is its control.
- **Rejected:** *any failing check counts.* It is already true for every run
  (`validate.ts:267`), so it would bind nothing R16 adds. *Matching the check's
  name or text against the steps.* It is a heuristic that passes on wording.
- **Reverse:** drop `reproduces`, and rely on the rubric alone.

### D-A-BG-06: a report that never becomes a spec is recorded beside the runs

- **Found:** the entry says such a report is recorded in P14's record, but P14
  keeps a run's record and a dismissed report has no run.
- **Chosen (A-R16-05):** the Vault gains `dismissCandidate(id, cause, at)`, and
  `IntakeEntry` gains `dismissed: { cause, at } | null`. `DismissalCause` is
  closed: `not-a-defect`, `duplicate`, `insufficient-detail`,
  `not-reproducible`. `POST /intake/:id/dismiss` takes the cause and no text. A
  dismissed candidate admits no run. A dismissal and an expiry are decisions
  kept beside the runs, as R22 keeps a delivery's (D-R22-03). A refusal at
  `spec` or at the `test-design` exit stays in its run's P14 record. Both carry
  the template, so R2 can count by it. The entry's wording is corrected to
  match.
- **Rejected:** *a free-text reason.* A person reading a report could paste
  its text there, and R13b's findings review reads these records. *An empty
  run record for a dismissal.* It would put a run nobody admitted into R2's
  counts.
- **Reverse:** count expiries alone, and drop dismissal.

### D-A-BG-07: extracted fields reach no prompt

- **Chosen:** the candidate's repository, number, and labels are recorded in
  the admission record and named in the run's report, and placed in no
  request. The drafter needs the defect, not the tracker's reference.
- **Consequence:** R16 does not call `narrowRun` with `'trigger-fields'`, so
  that source keeps R10's conformance as its only caller. It is not owed work:
  a later template that places fields in a prompt calls it then. A run whose
  author trust is below `narrowBelow` is still narrowed at admission under
  R10.
- **Rejected:** *labels given to the drafter, through `narrowRun`.* Every bug
  fix from a tracker would narrow for a hint the drafter does not need, and
  attacker-chosen bytes would enter a prompt, if only from an allowlist.
- **Reverse:** grant the fields to the spec drafter as input through
  `narrowRun('trigger-fields')`.

## R16: Bug-fix intake

Started on `v2` at 95b3d0a, after the amendment (#108). Builds A-R16-01 to
A-R16-05 as D-A-BG-02 to D-A-BG-07 chose them.

### D-R16-01: boundary, verified

- **Deliverables:**
  - `TemplateId` gains `'bug-fix'`, valid on `issue` alone; a `bug-fix`
    delivery records a candidate as `intake-candidate` does.
  - `TriggerPolicy.runTemplates`, the templates a person's own run may name,
    absent or empty by default; `RunRequest.template`; the admission record's
    `template`.
  - `Intent` a union: the R19 text arm, and the bug-fix arm of `steps`,
    `actual`, and `expected`; the intent record holds the parts as given.
  - A bug-fix run drafts both its spec and its tests, and is refused at
    admission with either supplied.
  - `SpecPart` gains `defect` and `reproduction`: the runtime writes
    `defect.json` before the drafter runs; the drafter writes
    `reproduction.json`; both lock with the spec.
  - A drafted or supplied check may declare `reproduces: true`, only with
    `onBase: 'fails'`; a bug-fix test draft needs a required one, and a run
    that is not a bug fix may declare none.
  - `Vault.dismissCandidate`, `IntakeEntry.dismissed`, the closed
    `DismissalCause`, and `POST /intake/:id/dismiss`.
  - The run report names the template and the candidate's issue.
  - The shipped `test-design` rubric gains the point that a check declaring
    `reproduces` follows the defect part's steps (D-A-BG-05).
  - Conformance assertions, one per sentence of the entry's conformance
    paragraph.
- **Out of scope (verbatim):** writing back to the tracker, such as asking the
  reporter for missing steps (a provider adapter); following the pull request
  through CI and review comments, whose text is untrusted for the same reason;
  seeding the data and accounts a reproduction needs (R1 probes whether a
  target can); finding defects that recur in one area (R11, R13); and a model
  that summarises reports for the person writing the spec.
- **Acceptance:** `pnpm typecheck`, `pnpm lint`, `pnpm test`, and
  `pnpm conformance` pass, and the registry holds an assertion for each
  clause of the conformance paragraph, each failing when its check is deleted.
- **Invariants:** I7 (no report text and no extracted field reaches a
  request), I4 (no run is a bug fix unless policy lists the template or the
  candidate's trigger routes to it), I3 (the runtime writes `defect`, and the
  test drafter sees only the locked spec), I5 (a missing part is refused,
  naming it). No pending registry entry is owed by R16; it adds its own.
- **Gate paths:** `packages/core/src/policy/types.ts`,
  `packages/core/src/station/types.ts`, `packages/integrity/src/types.ts`,
  `packages/vault/src/types.ts`, and `packages/conformance/`.

### D-R16-02: assumptions, each verified

- Dependencies shipped: `reviewed/R15`, `reviewed/R19`, `reviewed/P14`,
  `reviewed/R22` are tags on `origin` (`git tag -l 'reviewed/*'`).
- The `issue` schema carries no free text: repository, number, labels,
  author trust (`packages/core/src/trigger/schemas.ts:155-160`).
- A candidate's template is the policy's `taskTemplate[kind]`, never the
  payload's (`packages/api/src/intake.ts:132-147`), so a `bug-fix` route needs
  only the registry entry and the validator's kind check.
- A draft with problems cannot be approved (`packages/api/src/run.ts:337`)
  and cannot be locked (`packages/api/src/drafting.ts:793`), and the drafter
  is sent back while attempts remain (`drafting.ts:186-191`). So a problem
  recorded on the draft is a refusal at the station: nothing proceeds from it.
- Every run already needs a required check failing on the base
  (`packages/api/src/validate.ts:267`), and R15's base run is what proves a
  declared `'fails'` (`drafting.ts:192-205`).
- A candidate is spent by one exclusive file, `intake/admitted/<id>.json`
  (`packages/vault/src/local/vault.ts:1129-1133`).
- Every non-human kind enters at `intake` (`packages/core/src/policy/validation.ts:706-709`).

### D-R16-03: where the code differs from the entry

- **"Entered at `spec`."** The validator keeps every kind at `intake`, where
  admission runs. A bug-fix run's first work is the spec draft, so it is
  entered at `spec` in the only sense the line has: `intake` does nothing
  but admit. No validator change.
- **"Both carry the template."** A P14 decision names its run, and the run's
  admission record names the template; a dismissal names its candidate,
  whose record names the template. No copy is added to each decision, which
  could disagree with the record it copies.

### D-R16-04: the defect and reproduction checks are draft problems

- **Chosen:** in a bug-fix run the spec draft must hold `defect.json` with
  exactly the runtime's bytes and a `reproduction.json` that parses; any
  other is a problem on the draft, naming the file (`missing`,
  `not-the-intent`, `not-a-spec-part`). A problem sends the draft back, and
  on the last attempt a draft with problems cannot be approved. The
  `test-design` entry then re-checks the locked parts, as it does the
  security part, refusing `spec-part-missing` naming `defect` or
  `reproduction`.
- **Why:** the drafted spec is the only spec a bug-fix run has, and the draft
  read is the one place its bytes are judged before anything locks them.
- **Rejected:** *a new `StationRefusal` arm for a defect mismatch.* No locked
  defect can differ from the runtime's bytes once the draft read refuses it,
  so the arm would be unreachable.
- **Reverse:** add the arm and check at the `spec` exit.

### D-R16-05: `reproduces` sits on acceptance and behavioral checks

- **Ambiguous:** A-R16-04 says `AcceptanceCheckSpec` gains it, while the
  rule it extends (`validate.ts:267`) counts acceptance and behavioral
  checks alike, and `deniesRule` sits on both (`DenialFields`).
- **Chosen:** both, beside `deniesRule`. A defect in a CLI or an HTTP surface
  is reproduced by a behavioral check.
- **Rejected:** *acceptance only.* A bug fix in a stack with no test adapter
  could not declare its reproduction at all.
- **Reverse:** move the field to `AcceptanceCheckSpec`.

### D-R16-06: a dismissal and an admission share one exclusive file

- **Chosen:** `dismissCandidate` writes the same exclusive file
  `markCandidateAdmitted` does, holding `{ dismissed: { cause, at } }` in
  place of `{ runId }`. Whichever is first wins, and the other returns
  `false`.
- **Rejected:** *a second file for dismissals.* A dismissal and an admission
  racing could both succeed.
- **Reverse:** a separate file, with a lock across both.

### D-R16-07: the template is resolved before the intent is checked

- **Chosen:** admission reads the candidate's template before the drafting
  checks, by a read with no side effect, since the template decides what
  intent is valid. The existing read that marks expiry stays where it is.
- **Reverse:** move the template checks after the candidate read.

### D-R16-08: only the HTTP route takes a bug-fix intent

- **Chosen:** `POST /runs` takes `template` and, with it, an `intent` object
  of the three parts. The CLI's `--intent` stays text; a bug-fix flag set
  is a client change noted for later.
- **Reverse:** add `--bug-fix --steps --actual --expected` to the CLI.

### D-R16-09: each assertion fails when its check is deleted (I8)

Thirteen mutants, each one check removed, run against the assertion that
claims it; every one failed it: the defect bytes check and the locked parts
(`I3.bug-fix-spec-carries-the-defect`); the drafted and the parsed
`reproduces` rules (`I5.bug-fix-tests-need-a-reproduction`); the intent's
parts (`I5.bug-fix-intent-needs-its-parts`); the `runTemplates` grant and the
candidate's template (`I4.run-template-granted-by-policy`); the dismissed
check and the shared spend mark (`I5.dismissed-candidate-admits-no-run`); the
validator's kind check (`I4.bug-fix-template-valid-on-issue-alone`); the
supplied-spec and supplied-reproduction refusals
(`I3.bug-fix-run-drafts-both-artifacts`); and the report's issue
(`I7.bug-fix-run-sends-no-report-text`). The absence of report text in every
request is a property, not a check, so it has no single mutant: the assertion
seats a stub in every seat and fails on any marker, body, or field byte.

### D-R16-10: POST /runs reads a three-part intent without a template (review fix, codex-2)

- **Found:** `createBody` read an object intent only when the body named
  `template: 'bug-fix'`, so a run from a bug-fix candidate, which takes the
  candidate's template without naming it, was refused 400 before admission
  could resolve the template.
- **Chosen:** the route reads either shape whatever the body names, and
  admission, which resolves the template, refuses a shape that does not fit:
  a three-part intent in a run with no template is `not-applicable`.
- **Rejected:** *requiring `template` beside `candidate`.* It restates what
  the candidate already fixes, and a mismatch is already refused.
- **Reverse:** read the object shape only beside `template: 'bug-fix'`.
