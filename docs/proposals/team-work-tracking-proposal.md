# Team Work Tracking & Context Sharing Strategy

**Bridging AI-Assisted Development with Azure DevOps for Team Visibility**

**Date:** March 25, 2026

---

## Executive Summary

Our team uses AI-assisted development workflows (AI-DLC) through Olympus to manage feature lifecycle from requirements through construction. Individual developers have strong local tracking (progress, artifacts, quality metrics) but team-level visibility and context sharing across roles is lacking.

This proposal outlines a strategy to integrate Olympus with Azure DevOps so that:

- Developers stay productive in their Claude Code sessions
- Managers and team members see progress in Azure DevOps
- Handoffs between roles (requirements, coding, testing) carry full context automatically

---

## The Problem

When multiple people work on a feature through AI-DLC stages (requirements, design, coding, testing), three tensions emerge:

| Need | Best Location | Current Problem |
|------|--------------|---------|
| Feature/requirement context | Azure DevOps | Not consumable by Claude in dev sessions |
| Technical/code context | Repository | Not visible to non-developers or across team |
| Progress/status | Both | Risk of drift between the two |

Currently, Olympus tracks work per-developer locally with checkpoint files, state files, and artifact trees. This works well for individuals but doesn't address:

- How does a tester pick up where a requirements author left off?
- How does a manager see progress across all in-flight features?
- How do team decisions and context flow to whoever needs them?

---

## Proposed Solution: Two-Tier Artifact Model

### Architecture Overview

The solution separates concerns into two systems that exchange information through standardized bridges:

```
Azure DevOps (Team Source of Truth)          Repository (Dev Source of Truth)
========================================      ==============================
| Work Item #4521                  |         | aidlc-docs/payment-refund/   |
|  - Acceptance criteria           |<------->|   intent.md                  |
|  - Business rules                |  links  |   functional-design.md       |
|  - Status: In Construction       |  &      |   checkpoint.json            |
|  - Assigned: Mike (code)         | context |   nfr-design.md              |
|  - Team comments/decisions       |         |                              |
========================================      ==============================
```

**Core Principle:** Don't duplicate content. Store a link and fetch on demand.

- **Azure DevOps** holds the *what* and *why* (features, requirements, acceptance criteria, status, team assignments)
- **The repository** holds the *how* (design decisions, code context, technical artifacts)
- **YAML frontmatter** in repository artifacts provides the bridge between the two

---

## Component 1: YAML Frontmatter Linkage

Every AI-DLC artifact generated by Olympus gets a standardized header linking it to Azure DevOps:

```yaml
---
devops_id: 4521
devops_type: UserStory
iteration: Sprint 12
last_synced: 2026-03-25T10:55:00Z
---

# Functional Design: Payment Refund Processing
[artifact content follows]
```

This lightweight linkage:
- Doesn't duplicate content between systems
- Gives both humans and AI a breadcrumb to follow
- Can be added automatically by Olympus when a DevOps work item ID is provided at workflow start

---

## Component 2: Azure DevOps MCP Connector

The highest-leverage piece. An MCP (Model Context Protocol) server connects Claude Code sessions to Azure DevOps APIs. Developers never leave their IDE to get team context.

**How it works in practice:**

1. Developer starts a workflow with `/plan` and provides a DevOps work item ID
2. MCP pulls acceptance criteria, linked items, team comments, and prior decisions into the Claude session
3. During construction, Claude has both repository artifacts AND DevOps context
4. On stage completion, MCP pushes a structured status update back to DevOps

**Benefits:**

- Developers stay in their Claude Code / VS Code workflow
- No manual context copying or tab-switching between tools
- Bi-directional: context flows in, status flows out
- Team decisions made in DevOps comments automatically inform Claude's work

---

## Component 3: Azure DevOps as the Team Dashboard

Rather than building a separate dashboard, push structured updates from Olympus to Azure DevOps so existing boards and queries reflect AI-DLC progress.

**Example of what a work item would show after Olympus integration:**

```
DevOps Work Item #4521 - Payment Refund Processing

Status: In Construction
AI-DLC Stage: Code Generation (Unit 2/3 complete)
Tags: [ai-dlc, inception-complete, construction-active]
Progress: 65%

Auto-Generated Update:
  "Functional design approved. 2 of 3 construction units complete.
   86% test coverage on completed units. Next: Final unit implementation."
```

This gives managers and non-developer team members visibility into AI-assisted work without requiring them to understand Olympus internals. They use the same DevOps boards and queries they already know.

---

## Component 4: Role-Based Context for Handoffs

The handoff problem—one person does requirements, another codes, another tests—is solved by combining the above components:

| Role | Needs From Others | Gets It From |
|------|-------------------|-------------|
| Requirements Author | Business context, prior decisions | Azure DevOps work items and comments |
| Developer | Requirements, design decisions, acceptance criteria | MCP pulls from DevOps + reads repository artifacts |
| Tester | Requirements, what was built, known risks | MCP pulls from DevOps + reads repository artifacts + checkpoint quality data |

Repository artifacts (intent.md, functional-design.md, checkpoint.json) become the handoff documents. They're committed to feature branches, linked to DevOps via frontmatter, and consumable by Claude in any team member's session.

## What Already Exists

Olympus already has significant tracking infrastructure built and active:

| Component | Status | What It Does |
|-----------|--------|-------------|
| Checkpoint system | Built, active | Tracks phase/stage progress, artifacts, test results, security findings, coverage % per feature |
| Status reporter | Built, active | Generates formatted progress reports with progress bars, artifact trees, risk/gate summaries |
| Developer dashboard | Built, active | `/workflow-status` command showing current feature progress |
| Session state tracking | Built, active | Token budget, prompt history, agent performance metrics |
| Learning/efficiency system | Built, active | Per-agent success rates, token costs, trend analysis for optimization |
| State file generator | Built, active | Human-readable Markdown progress files committed to repository |

**What needs to be built:**

- Azure DevOps MCP connector (the bridge)
- YAML frontmatter generation in artifact templates
- DevOps push-back on stage transitions
- Handoff metadata in checkpoint schema
- Team-level aggregation view (or DevOps query templates)

---

## Implementation Approach

### Phase 1: Foundation (Low effort, immediate value)

- Add YAML frontmatter support to Olympus artifact generators
- Accept a DevOps work item ID at `/plan` workflow start
- Commit checkpoint.json to feature branches for team consumption
- **Outcome:** Artifacts are linkable to DevOps; team members can find repository context from work items

### Phase 2: MCP Integration (Medium effort, high value)

- Build Azure DevOps MCP server (read work items, comments, linked items)
- Pull DevOps context into Claude sessions on workflow start
- Push status updates to DevOps on stage transitions
- **Outcome:** Developers have full context in Claude; managers see progress in DevOps without manual updates

### Phase 3: Team Features (Medium effort, team-scale value)

- Add handoff/role fields to checkpoint schema
- Create DevOps query templates for AI-DLC progress views
- Build team-level aggregation (all in-flight features across team)
- **Outcome:** Managers have team-wide visibility; handoffs include full context

---

## Key Design Decisions

1. **Azure DevOps is the team dashboard** — Don't build a second dashboard; push data to where the team already looks.

2. **Don't duplicate content** — Store links (frontmatter IDs) and fetch on demand (MCP), not copies. Single source of truth per system.

3. **MCP is the bridge** — Developers stay in Claude Code, non-developers stay in DevOps, data flows between automatically.

4. **Checkpoint.json evolves incrementally** — Already tracks quality metrics; add team/handoff fields as phases are implemented.

5. **Artifact linkage is forward-compatible** — YAML frontmatter can be ignored by existing tooling; new tooling can use it when ready.

---

## Risks & Mitigations

| Risk | Impact | Mitigation |
|------|--------|-----------|
| DevOps API availability affects dev sessions | High | Cache context locally; degrade gracefully if MCP unavailable |
| Frontmatter format evolves and breaks | Medium | Version the schema; support multiple versions during transition |
| Team members forget to provide DevOps ID | Medium | Make it optional; provide fallback workflow without DevOps linkage |
| Duplicate/stale context between systems | Medium | MCP always reads DevOps live; repository is read-only for MCP |

## Conclusion

This strategy leverages what Olympus already tracks locally and extends it to team visibility through Azure DevOps without duplication or disrupting developer workflows. The phased approach allows us to start immediately (Phase 1) while building toward full team-scale benefits (Phase 3) over time.

The result is a unified system where individual developers work efficiently in Claude Code, managers see progress in Azure DevOps, and context flows seamlessly between roles—all without manual synchronization.
